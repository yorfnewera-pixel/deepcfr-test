Ниже — **один конкретный план для coding-агента**: строим общую карточную абстракцию для стола максимум на 8 игроков, учитывающую карточную силу против **1–7 соперников**. Это не перенос HU-стратегии и не симуляция других турнирных столов.

# 1. Что сейчас делает утилита

В текущем коде:

- выбираются уникальные канонические ситуации `две карты героя + борд`;
- на флопе и тёрне сэмплируются будущие борды и **одна** рука соперника;
- на ривере equity против одного случайного соперника считается полным перебором;
- строится профиль из **27 признаков**: средняя equity, стандартное отклонение, пять квантилей и гистограмма из 20 корзин;
- для каждой улицы отдельно обучается `StandardScaler + KMeans`;
- по умолчанию используются 100 000 train-ситуаций, 20 000 holdout и 200 кластеров;
- дополнительно создаётся таблица 169 префлоп-классов. [equity.py](https://github.com/yorfnewera-pixel/deepcfr-test/blob/main/src/card_abstraction/equity.py) · [features.py](https://github.com/yorfnewera-pixel/deepcfr-test/blob/main/src/card_abstraction/features.py) · [pipeline.py](https://github.com/yorfnewera-pixel/deepcfr-test/blob/main/src/card_abstraction/pipeline.py)

**Проблема для 8-max:** профиль описывает силу руки против одного соперника. Он не описывает, как меняется её сила и потенциал против нескольких соперников.

Но нельзя просто заменить «один соперник» на «семь»: за 8-max столом после фолдов часто остаются два, три или четыре участника раздачи.

# 2. Зафиксировать контракт новой абстракции

Предлагаю такой контракт:

```text
Название: multiway_postflop_card_abstraction_v1
Максимум мест: 8
Карточные сценарии: герой против 1, 2, ..., 7 соперников
Улицы: flop, turn, river
Reference ranges: uniform random legal hands
Выход: общий bucket_id для карточной ситуации каждой улицы
```

Для одной карточной ситуации строим **совместный профиль**:

\[
F(H,B)=
[F_1(H,B),F_2(H,B),\ldots,F_7(H,B)],
\]

где \(F_k\) — профиль showdown equity против \(k\) случайных соперников.

Сохраняем текущую структуру каждого блока:

\[
7 \times 27 = 189
\]

признаков.

**Один набор кластеров на улицу, обученный на всех семи блоках одновременно.** Не семь независимых таблиц и не один профиль только против семерых.

Это позволяет объединять карточные ситуации, похожие не только по HU-equity, но и по тому, **как их сила меняется с количеством соперников**.

### Что в эту абстракцию не включать

Не включать в карточный bucket:

- стеки;
- позиции;
- ante;
- размеры банков;
- выплаты;
- количество оставшихся игроков турнира;
- расстояние до баббла;
- историю ставок.

Эти данные остаются отдельными входами MTT-policy и tournament value.

**Карточная equity — не $EV.** Утилита описывает свойства карт; турнирный блок определяет стоимость исходов. Нельзя назвать 189-мерный equity-профиль «готовой MTT-абстракцией всей ситуации».

# 3. Переделать расчёт equity: совместная раздача без повторов

Основное изменение — `src/card_abstraction/equity.py`.

Сейчас `_payoff` использует `compare_showdown` для одной руки соперника. Новый код должен оценивать **долю одного общего банка**, которую герой получает при showdown против нескольких рук. [equity.py](https://github.com/yorfnewera-pixel/deepcfr-test/blob/main/src/card_abstraction/equity.py)

Для одного сэмпла:

1. Зафиксировать карты героя и полный борд.
2. Удалить эти карты из доступной колоды.
3. Выбрать **14 различных карт** для семи соперников.
4. Разбить их на семь двухкарточных рук.
5. Оценить силу каждой руки.
6. Рассчитать результат героя против первых 1, 2, …, 7 соперников.

Последний пункт позволяет использовать один сэмпл сразу для всех семи профилей.

### Как учитывать ничьи

Для \(k\) соперников:

\[
w_k=
\begin{cases}
0, & \text{хотя бы один соперник сильнее героя},\\
\dfrac{1}{1+m}, & \text{герой делит лучшую руку с }m\text{ соперниками}.
\end{cases}
\]

**Не брать среднее семи попарных побед.** Герой может победить шестерых и проиграть одному — его доля общего банка тогда ноль, а не \(6/7\).

**Не сэмплировать семь рук независимо с возвращением карт.** Все руки в одном showdown должны быть совместимы друг с другом.

### Важное ограничение

Это reference-equity против **равномерных случайных рук**, не equity против реальных диапазонов после ставок.

Неизвестные карты уже сфолдивших игроков в первой версии отдельно не моделируем: расчёт задаёт нейтральный карточный reference, а не posterior по полной истории. Это ограничение записать в manifest и документацию.

# 4. Сохранить смысл «профиля будущей equity»

На флопе и тёрне нужно сохранить двухуровневую структуру текущего расчёта:

```text
карты героя + текущий борд
    → набор будущих полных бордов
    → для каждого борда equity против k соперников
    → распределение этих equity по будущим бордам
```

Для каждой ситуации получить матрицу:

```python
equities.shape == (runout_samples, 7)
```

Столбец `k-1` — conditional equity против \(k\) соперников на каждом будущем борде.

**Не строить гистограмму отдельных исходов `0 / 1 / доля ничьей`.** Такая гистограмма потеряет смысл текущей абстракции: она должна отражать распределение *оценённой equity по runout*, а не распределение побед и поражений одного showdown.

### Ривер

На ривере будущего борда нет:

```python
equities.shape == (1, 7)
```

- Против одного соперника можно сохранить точный перебор как oracle.
- Против 2–7 соперников использовать совместный Monte Carlo.
- Для этих столбцов явно обозначать `estimate`, а не `exact`.

Здесь стандартное отклонение внутри 27-мерного блока будет нулевым, поскольку борд фиксирован. **Не путать это с отсутствием Monte Carlo-погрешности:** погрешность оценки нужно хранить отдельно в диагностике.

# 5. Использовать парные сэмплы для воспроизводимости

Один и тот же набор соперников должен использоваться для сравнения:

```text
1 opponent: первые 2 карты
2 opponents: первые 4 карты
...
7 opponents: все 14 карт
```

При фиксированном борде и конкретной последовательности рук добавление соперника не может увеличить долю банка героя. Это даёт полезный тест:

\[
w_{k+1}\le w_k.
\]

Для итоговых MC-оценок использовать ту же вложенную выборку — тогда сравнение профилей будет менее шумным.

В seed/key включить:

- версию estimator;
- master seed;
- канонический ключ ситуации;
- тип вычисления: runout или showdown sampling.

**Число сэмплов не включать в seed потока**, чтобы увеличение бюджета могло продолжать ту же последовательность случайных событий. Но бюджеты обязательно записывать в идентификатор кэша и manifest.

# 6. Перестроить `features.py`

Предлагаемый интерфейс:

```python
build_feature(
    situation,
    *,
    spec,
) -> np.ndarray  # shape: (189,)
```

Порядок признаков зафиксировать:

```text
opponents_1:
    mean, std, q10, q25, q50, q75, q90, histogram[20]
opponents_2:
    ...
...
opponents_7:
    ...
```

Проверки:

- форма строго `(189,)`;
- все значения конечны;
- equity и квантили в `[0, 1]`;
- каждая гистограмма суммируется в 1;
- порядок квантилей не нарушен;
- перестановка мастей не меняет профиль при том же seed;
- одинаковые входы воспроизводят одинаковый результат.

**189 — размер новой reference-feature, не обязательный размер входа policy.** В дальнейшем policy может получать bucket embedding, исходные карточные признаки и контекст отдельно.

# 7. Канонизацию оставить, но обозначить её границы

Текущий `canonicalize` перебирает все 24 перестановки мастей и строит ключ только из карт героя, борда и улицы. Это подходит для новой **карточной** абстракции; количество мест само по себе не требует добавлять семь скрытых рук в ключ. [canonical.py](https://github.com/yorfnewera-pixel/deepcfr-test/blob/main/src/card_abstraction/canonical.py) · [domain.py](https://github.com/yorfnewera-pixel/deepcfr-test/blob/main/src/card_abstraction/domain.py)

В `CardSituation` по-прежнему должны быть только:

```text
hero cards
public board
street
```

Руки соперников — временные сэмплы estimator, а не часть входа агента.

Отдельно документировать: карточный ключ не сохраняет порядок появления отдельных карт борда и не является полным information-set key. Публичная история и её связь с улицами остаются в игровом encoder.

# 8. Исправить выборку train/holdout

Сейчас train и holdout создаются двумя независимыми вызовами `sample_unique_situations` с соседними seeds. Уникальность проверяется внутри каждой выборки, но **взаимное пересечение не исключается явно**. [dataset.py](https://github.com/yorfnewera-pixel/deepcfr-test/blob/main/src/card_abstraction/dataset.py) · [pipeline.py](https://github.com/yorfnewera-pixel/deepcfr-test/blob/main/src/card_abstraction/pipeline.py)

Нужно:

- добавить `excluded_keys`;
- исключить все train-ключи при построении holdout;
- сохранить ключи обеих выборок;
- проверить `train_keys ∩ holdout_keys == ∅`.

Основную выборку оставить карточной, без запуска турниров.

Дополнительно создать **небольшой диагностический набор** известных типов ситуаций: сильные готовые руки, слабые пары, дро, монотонные и спаренные борды, общий натс на борде. Его задача — ловить очевидные ошибки и видеть содержимое buckets, а не подменять train-распределение.

# 9. Ускорить estimator до большого build

Новый расчёт существенно тяжелее HU. Поэтому **не запускать сразу 100 000 × 3 улицы на Python-циклах**.

Предпочтительное изменение Rust/Python API:

```text
evaluate_many_showdowns(...)
```

или специализированный batch-estimator, который:

- принимает карточную ситуацию и sampling budget;
- оценивает героя один раз на каждом полном борде;
- оценивает семь рук соперников;
- сразу возвращает результаты для 1–7 соперников.

Если пока использовать попарный `compare_showdown`, сначала проверить его наличие в обновлённом движке: текущий код абстракций от него зависит.

Добавить:

- chunked processing;
- кэш feature по каноническому ключу и полному spec;
- сохранение промежуточных shards;
- resume после остановки;
- измерение скорости и пикового потребления памяти.

**Параллелизм вычисления независимых карточных сэмплов допустим. Это не симуляция нескольких турнирных столов.**

# 10. Обновить кластеризацию и quality gates

На каждой улице отдельно:

1. Построить 189-мерные train-features.
2. Обучить scaler **только на train**.
3. Обучить KMeans.
4. Назначить holdout buckets.
5. Посчитать качество в исходном equity-пространстве и в пространстве кластеризации.

Не объявлять 200 buckets достаточными только потому, что столько было в HU. Оставить число кластеров параметром; решение о production-бюджете принять после измерения ошибки.

### Обязательные отчёты

- размеры buckets;
- пустые buckets;
- train/holdout distances;
- ошибка внутри buckets **отдельно для каждого числа соперников**;
- разброс средней equity внутри bucket;
- примеры близких и далёких от центра карточных ситуаций;
- стабильность назначения при увеличении MC-бюджета.

Текущая проверка стабильности исключает river, поскольку HU river exact. **В новой версии river тоже нужно проверять**, поскольку его multiway-профили будут MC-оценками. [pipeline.py](https://github.com/yorfnewera-pixel/deepcfr-test/blob/main/src/card_abstraction/pipeline.py)

Порог 95% стабильности можно оставить начальной целевой настройкой, но не считать автоматически доказанным стандартом для 189 признаков. Пограничные назначения отдельно оценивать по расстоянию до двух ближайших центров: смена bucket возле границы не всегда означает большую карточную ошибку.

# 13. Префлоп и подключение к MTT

Таблицу 169 классов можно оставить: она описывает тип двухкарточной руки с учётом мастевой симметрии, а не HU-стратегию. Но в документации исправить формулировку: это **169 карточных классов**, не 169 полных префлоп-ситуаций 8-max. Позиции, стеки, история и турнирные стимулы остаются отдельно. [preflop.py](https://github.com/yorfnewera-pixel/deepcfr-test/blob/main/src/card_abstraction/preflop.py)

Для runtime предусмотреть:

```text
карты героя + борд
    → canonical key
    → cached feature / проверенный estimator
    → street artifact
    → bucket_id
```

Количество ещё не сфолдивших соперников, включая all-in участников, передаётся policy **отдельным признаком**. При side pots нельзя оценить денежный исход одним общим equity: eligibility по каждому банку рассчитывает движок.

**Не вызывать дорогой MC-build заново в каждом узле CFR.** Нужен кэш с ограничением памяти; полный offline dataset из 100 000 ситуаций не покрывает все возможные борды, поэтому поведение на неизвестном ключе требуется определить заранее.

# 14. Порядок TDD-задач

Передай агенту именно такую последовательность:

1. Создать `AbstractionSpec` с фиксированным layout на 189 признаков.
2. Написать тесты multiway pot share: победа, проигрыш одному, ничьи на 2–8 игроков.
3. Реализовать совместное сэмплирование рук без повторов карт.
4. Реализовать матрицу conditional equities для 1–7 соперников.
5. Проверить HU-столбец против exact river oracle и multiway-столбцы против небольших перебираемых test-fixtures.
6. Переделать `build_feature`.
7. Исключить пересечения train/holdout.
8. Обновить pipeline, manifests, loader и CLI.
9. Добавить кэш, resume и замеры производительности.
10. Выполнить smoke-build, затем ограниченный build с проверкой MC-стабильности.
11. Только после этого запускать production-build и подключать buckets к MTT-encoder.

**Итоговый контракт:** переделываем существующий HU offline-пайплайн в **совместную multiway-карточную абстракцию для 8-max**, а не в «equity только против семерых». Турнирные выплаты и баббл остаются в tournament value, разные стеки и side pots — в движке, реальные диапазоны соперников — в отдельной модели информации. Такое разделение позволит не спутать карточную абстракцию с готовой турнирной стратегией.
