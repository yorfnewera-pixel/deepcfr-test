## 0. Две конкурирующие работы

В репозитории лежат две статьи о параллелизации CFR. Они предлагают **разные** подходы, и статья A прямо критикует статью B.

| | A | B |
|---|---|---|
| Авторы | Boning Li, Longbo Huang (Tsinghua IIIS) | Juho Kim, **Tuomas Sandholm** (CMU) |
| Название | Real-Time Parallel CFR | Parallelizing CFR (NeurIPS 2026 submission) |
| Подход | конвейер из 7 стадий, CPU+GPU | CFR как линейная алгебра, GPU |
| Целевой режим | real-time depth-limited solving | табличный CFR на полностью перечислимых играх |
| Ускорение | 3.3–3.4× на 5 потоках | до 4×10³ против C++ OpenSpiel |

Критика A в адрес B (дословно из Related Work статьи A): *«does not support basic components in real-time game solving pipelines such as depth-limited solving and pruning, and its parallel implementation on GPU is much slower than the most advanced CFR implementation methods on single threaded CPU»*.

Обе частично правы: B выигрывает на огромных перечислимых деревьях, проигрывает на малых (см. §2.3).

## 1. Статья A: Real-Time Parallel CFR (Tsinghua)

Путь: `/Real-Time Parallel Counterfactual Regret Minimization/main.tex`

> Внимание: в той же папке лежит `outline.md` — это **другая статья** (WarmupEV / информационная абстракция). Не путать.

### 1.1. Конвейер

Итерация CFR разбита на 7 стадий, две ортогональные оси параллелизма: **по инфосетам** и **по узлам дерева**.

| Стадия | Операция | Ось |
|---|---|---|
| S1 | ForwardProfile | инфосет |
| S2 | AggregateProbSum | узел × карта |
| S3 | OpponentReach (π₋ᵢ) | узел, затем инфосет |
| S4 | ShowdownEquity | узел |
| S5 | BatchLeafEval | GPU batch |
| S6 | BackwardCFV | узел + инфосет |
| S7 | UpdateRegret | инфосет |

После S2 конвейер **разветвляется**: S3+S4 (CPU) идут параллельно с S5 (GPU) — между ними нет зависимости по данным. Затем join, S6+S7.

Конвейер **вычислительно точен**: результат численно идентичен последовательному CFR. От варианта CFR зависит **только S7**; S1–S6 одинаковы для Vanilla / CFR+ / DCFR / Linear / PCFR+.

### 1.2. Приёмы

- Работа на уровне **инфосетов**, не историй: все руки инфосета делят стратегию, значит векторизуются.
- Три уровня агрегатов reach: `P_sum[n]`, `P_card[n][c]`, `P_hand[n][h]` + включение-исключение → блокировка карт за **O(1)** вместо O(|H|²).
- Showdown: ранги задают полный порядок → линейный проход по отсортированным рангам, **O(n)** вместо O(n²) (Johanson 2011).
- OpenMP (CPU) + LibTorch (GPU).
- EVPA-прунинг как **препроцессинг** → мультипликативное ускорение всех стадий, до 2 порядков.
- Абстракция по умолчанию lossless.

### 1.3. Цифры

Железо: NVIDIA DGX Spark (GB10 Grace Blackwell), 5 CPU-потоков + 1 GPU.
Дерево: SPR=64, |A_raise|=3 → **2 006 256 инфосетов / 1 084 381 368 историй**.

### 1.4. Три места, где статья подтверждает НАШИ замеры

Самая полезная часть документа.

**1) Конкуренция за L3.** Они пинят потоки на 5 больших ядер внутри одного L3-кластера и пишут: *«memory bandwidth becomes a bottleneck as multiple threads compete for shared L3 cache»*. Ровно то, что измерил агент:

| threads | mean | p99 | max |
|---|---|---|---|
| 1 | 0.051 мс | 0.088 | 0.252 |
| 4 | 0.074 мс | 0.232 | **8.9 мс** |

→ `torch.set_num_threads(1)` (#107 §1.1, §6 п.2) не хак, а известное свойство железа.

**2) S3 + S6 доминируют.** OpponentReach + BackwardCFV вместе — **>50% конвейера** на флопе и терне. У нас ветка оппонента 83.5 с против ветки героя 25.2 с, те же ~3.3×.
→ **Асимметрия структурна. Баг в ветке оппонента искать не надо** (#107 §1.3).

**3) Меньше бакетов — дешевле.** B=50 против 169 даёт 3×.
→ Намёк, что 15 анкеров сайзинга внутри солвера можно резать без большого вреда (ср. `solver_sizing_source`, отложенный `blueprint_buckets`).

### 1.5. Почему нельзя скопировать

- HUNL, **два игрока, zero-sum**. У нас 6-max multiway: математика инфосетов и блокировки карт так не факторизуется.
- Нужен GPU для S5. У нас `torch 2.11.0+cpu`, CUDA недоступна.
- Векторизация по инфосетам предполагает обработку всех рук инфосета вместе. У нас Python-DFS по узлам, `batch=1`.
- BFS-подобная структура ломает детерминизм, на котором держится S2-харнесс (#106 §4.6, #107).

## 2. Статья B: Parallelizing CFR (Sandholm)

Путь: `/Parallelizing Counterfactual Regret Minimization/neurips_2026.tex`

### 2.1. Идея

Никакого конвейера. **Sequence-form CFR переписывается целиком как линейная алгебра**, дальше параллелизм берётся бесплатно из библиотечных примитивов (CuPy / cuSPARSE).

Три **logic-матрицы** (элементы из {0,1}):

- `A` (P × Σ), `A[p,(j,a)] = 1[p = ρ(j,a)]` — перевод «по секвенциям» ↔ «по узлам»: `z = A z'`, `z' = Aᵀ z`.
- `B = A[:,2:]` — то же для непустых секвенций (behavioral representation).
- `C` (J × Σ⁺), `C[j,(j',a)] = 1[j=j']` — суммы по действиям внутри решающей точки. `Cᵀ(C z)` разносит суммы обратно → L1-нормировка = поэлементное `z / (Cᵀ C z)`. Это и есть regret matching.

Обход дерева = **уровневые матрицы смежности** `L^(d)`, по одной на глубину. `L^(1) … L^(k)` даёт top-down проход, обратный порядок — bottom-up. Идея из **GraphBLAS**: matvec с матрицей смежности = один шаг BFS.

Вся итерация = ~8 разреженных matvec + пара Hadamard-операций:

```
NextStrategy():
  b = (r)+ / (C^T(C (r)+))              # поэлементное деление
  y = e_root
  for L^(d), top-down:   y = y + (L^(d))^T y
  x = A^T y
  return x

ObserveUtility(u):
  v = 0
  w = A u
  for L^(d), bottom-up:  v = v + L^(d) w + L^(d) v
  q = B^T (w + v)
  r = r + q - C^T(C (b * q))            # b*q поэлементно
```

### 2.2. Сложность и варианты

Work-depth модель, CSR:

- work `W = Θ(|P|)` — столько же, сколько у последовательного sequence-form CFR. **Без параллелизма ничего не теряется.**
- depth `D = Θ(k log B)`, `k` — высота TFSDP, `B` — степень.
- параллелизм `= |P| / (k log B)`.
- память `Θ(|P|)`.

Контринтуитивно: рост ветвления `B` **снижает** параллелизм (глубина скалярного произведения в CSR matvec). Но на практике рост `log B` уменьшает высоту `k`.

Варианты CFR — одна строчка:

| Вариант | Добавка в конец ObserveUtility |
|---|---|
| CFR+ | `r ← (r)⁺` |
| DCFR | `r ← r * (t^α/(t^α+1) если r>0; t^β/(t^β+1) если r<0; 1 если r=0)` |
| PCFR/PCFR+ | бэкап `r`, переиспользовать `b^(t−1)`, `ObserveUtility(m)`, `NextStrategy()`, восстановить `r` |

### 2.3. Цифры и КЛЮЧЕВАЯ ловушка

Железо: AMD Ryzen 9 3900X (12C/24T), 128 GB, RTX 4090 (16 384 CUDA-ядер). CuPy, double precision.

| Игра | # узлов | Ускорение vs C++ OpenSpiel |
|---|---|---|
| Kuhn poker | 58 | **−3.6×10²** (в 360 раз МЕДЛЕННЕЕ) |
| Leduc poker | 9.4×10³ | **−1.9** (медленнее) |
| Tiny battleship | 5.9×10⁴ | 6.9 |
| Liar's dice | 2.9×10⁵ | 1.5 |
| Small battleship | 2.3×10⁶ | 2.1×10² |
| Medium battleship | 1.5×10⁷ | 1.2×10³ |
| Large battleship | 5.2×10⁷ | **4.1×10³** |

Время итерации у их параллельной версии почти **не зависит** от размера игры: 14.3 / 25.2 / 24.2 / 38.6 / 25.7 / 19.4 / 22.0 мс. Это **чистый фиксированный оверхед запуска ядер**.

**Точка окупаемости ≈ 10⁴–10⁵ узлов.** Ниже неё GPU-подход проигрывает в 2–360 раз.

### 2.4. Побочный полезный факт

Статья повторяет рекомендацию Brown & Sandholm 2019: `(α, β) = (1.5, 0)` + квадратичное взвешивание вклада итераций в среднюю стратегию + alternating updates устойчиво бьёт CFR+.
→ Наш `discount_alpha: 1.5` подтверждён внешним источником. См. §4.

### 2.5. Применимость

**К блюпринт-тренеру — НЕ ПРИМЕНИМО ВООБЩЕ:**

1. Фреймворк **табличный**, требует полного перечисления дерева и `Θ(|P|)` памяти. У нас ~10³⁰⁰ ситуаций и сэмплированные обходы.
2. Статья сама пишет: MCCFR — **стохастическая** минимизация регрета (Farina et al. 2020), её схема параллелизации на табличный CFR **не переносится** и обратно тоже.
3. Нет нейросетей, depth-limited, прунинга, абстракций. `advantage_net` в этой картине не существует как объект.

**К солверу — концептуально да, численно нет.** Наши сабгеймы — ровно тот табличный перечислимый случай, для которого фреймворк написан. Но их размер (сотни-тысячи узлов) **ниже точки окупаемости**, а CUDA недоступна.

## 4. ЧТО НЕ ДЕЛАТЬ (главный раздел документа)

Зафиксировано, чтобы закрытые темы не открывались заново.

1. **Не переписывать солвер на CuPy/GPU.** CUDA недоступна (`torch 2.11.0+cpu`), а сабгеймы ниже точки окупаемости: на играх нашего размера подход проигрывает (Kuhn −360×, Leduc −1.9×).
2. **Не применять фреймворк Sandholm к блюпринт-тренеру.** Табличный, требует полного перечисления, MCCFR-схемы не переносятся ни в одну сторону.
3. **Не строить 7-стадийный конвейер статьи A.** Нужен GPU, two-player математика, плюс ломает детерминизм S2-харнесса.
4. **Не переоткрывать `discount_alpha: 1.5` / `discount_gamma: 1.0`.** Подтверждено и статьёй B (§2.4), и нашими результатами (#90b, #91, #91b, #100-A2).
5. **Не искать баг в ветке оппонента** из-за 83.5 с против 25.2 с. По статье A это структурное свойство (S3+S6 > 50% конвейера).
6. **Не поднимать `torch.get_num_threads()` выше 1 на обходе.** Конкуренция за L3 подтверждена и замером, и статьёй A. На обучении (`batch=1024`) — наоборот, потоки нужны.
7. **Не начинать level-batching без гистограммы глубин.** Гейт описан в #107 §6 п.9. Оценка «средний батч ≈ 9» — догадка, а не замер.
