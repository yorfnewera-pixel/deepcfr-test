## 1. Архитектурный контекст (нужен, чтобы §2 читался правильно)

Проект — **VR-DeepDCFR+**, а НЕ Brown-2019 Deep CFR. Ключевое отличие:

```
fresh_target = target_net(s) · discount + cf_regret
```

Накопление регрета живёт **в весах сети через бутстрап**, а не в буфере.

Отсюда два следствия, которые постоянно путают:

1. **Чистить advantage-буфер каждую итерацию — ПРАВИЛЬНО.** Накопление уже произошло в весах.
2. **Сеть должна быть персистентной.** Переинициализировать advantage-сеть между итерациями НЕЛЬЗЯ, это уничтожит всё накопление. (Эта ошибка была допущена в рекомендациях и отозвана.)

**Правило, выведенное из этого:**

> **Бутстрап есть → чистим буфер. Бутстрапа нет → резервуар.**

Применение правила по ногам:

| Буфер | Флаг | Бутстрап | Верно? |
|---|---|---|---|
| advantage (action) | `advantage_buffer_reservoir: false` | да | да, чистится |
| sizing advantage | `sizing_advantage_buffer_reservoir: true` | да | **противоречие**, см. §2.5 |
| strategy | резервуар | нет | да |
| sizing strategy | резервуар | нет | да |

> **Замечание 2026-08-13 (после T2a-bis).** Это противоречие оказалось не косметическим. Измерено: при `reservoir: true` в sizing-буфере только **17.7% строк fresh**, остальные 82.3% дают `target = clamp(net(s))` с градиентом ~1e-8. Эффективный батч 45 вместо 256, разрыв с action-ногой 2303× по сэмплам, несущим сигнал. Подробности в 107Result. **Это делает §2.5 приоритетным, а не опциональным.**

## 2. §2.6 — Пакет накопления (главный раздел)

Четыре элемента, применяются вместе. По отдельности каждый может не дать эффекта или навредить.

### 2.1. Бутстрап

```
fresh_target = sizing_target_net(s) · discount + cf_regret
```

`sizing_target_net` **уже создана** в `__init__` `deep_cfr.py`, отдельно её заводить не нужно. Проверено: синхронизируется с рабочей сетью через `load_state_dict` после каждого обучения (побитово идентичны).

### 2.2. Clamp (CFR+)

```
previous = clamp(previous, min=0)
```

Зачем: без него анкер, загнанный в отрицательный регрет, выбирается оттуда сотни итераций. С клампом — за одну.

У action-ноги уже стоит: `advantage_accumulation: dcfr_plus`.

**Это прямой ответ на возражение «боюсь отрицательных регретов, анкер застрянет».** Возражение верное, механизм от него уже есть.

### 2.3. Discount

```
discount_alpha: 1.5
discount_gamma: 1.0
```

**НЕ МЕНЯТЬ.** Закрыто результатами #90b / #91 / #91b / #100-A2. Дополнительно подтверждено внешним источником: Brown & Sandholm 2019 (AAAI) рекомендуют `(α, β) = (1.5, 0)` + квадратичное взвешивание вклада итераций + alternating updates, эта рекомендация повторена в Kim & Sandholm NeurIPS 2026 (разбор в #108 §2.4).

### 2.4. Функция потерь

```
advantage_loss: mse
```

Huber был попробован и **откачен**. `sizing_q` при этом сохраняет huber — это осознанное расхождение, не забытая правка.

### 2.5. Чистка sizing-буфера

По правилу из §1: у sizing-ноги бутстрап есть, значит `sizing_advantage_buffer_reservoir` должен быть `false`.

В оригинале #104 это стояло как «применить вместе с остальным пакетом», и вопрос «когда именно переключать» задавался отдельно (осталось без чёткого ответа).

> **Обновление 2026-08-13 (ред. 2).** Причина уточнена замерами (#107 §2.8 п. 10–11).
>
> **Правильное обоснование чистки — не «так велит правило §1», а механика бутстрапа.**
> Для stale-строки (`iteration != t`) таргет равен `previous = clamp(net(s))`, то есть **текущему
> выходу самой сети**. Такая строка не несёт информации: замер на 83 629 записях под маской
> показал `stale_loss = 0.0` и `|clamp(net) − net| max = 0.0`, clamp активен на 0 строках.
> Градиент от них **ровно нулевой**.
>
> Значит **накопление живёт в весах, а не в буфере.** Анкер A закредитован на iter 5 → ушёл в
> `previous` через бутстрап. Анкер B на iter 7 → `previous` уже содержит вклад A. Старая строка
> про A в буфере при этом не добавляет ничего.
>
> Ранний аргумент «резервуар нужен, потому что за визит кредитуется 1–3 анкера из 15 и полный
> вектор собирается только накоплением строк» — **неверен**. Полный вектор собирается бутстрапом.
>
> Практический масштаб проблемы: `SizingAdvantageBuffer.add` (`buffers.py:226-241`) — алгоритм R,
> `acceptance = capacity/_cur_id`, uniform по всей истории по замыслу. Доля свежих записей падает
> как `1/t`: **17.7% (iter 10) → 7.68% (20) → 5.31% (25) → 4.58% (30)**, прогноз 0.5% к iter 200.
> Эффективный батч при 10 шагах × 256: 453 → 117 сэмплов за итерацию. К переполнению capacity
> это отношения не имеет, деградация началась с первой итерации.
>
> Три варианта: **фильтр** (только fresh), **стратификация батча по свежести**
> (precedent: `buffers.py:415 sample_stratified`, флаг `sizing_q_stratified_sampling: true`),
> **`reservoir: false`**.
>
> **ВАЖНО — включать нельзя до П2.** Если stale не дают градиента, то стратификация меняет только
> эффективный размер батча по fresh-строкам, то есть это тот же фильтр помягче. Предельный случай
> измерен, и он **хуже**: фильтр (100% fresh) роняет `TV` 0.449 → 0.558. Причина в том, что
> сигнал смещён (`std(Q)/std(MC) = 0.189`), а больше смещённого сигнала — больше смещения.
> Код писать можно, флаг держать выключенным до результата П2 (#107 §6.2).

## 3. Три роли вероятностных полов — НЕ ПУТАТЬ

Одна из главных путаниц оригинала. Полы выполняют три разные функции в трёх разных местах:

| Где | Полы | Почему |
|---|---|---|
| **Traversal** | НЕТ | обход должен видеть распределение как есть |
| **Playing policy** | **ДА, ОБЯЗАТЕЛЬНО** | см. ниже |
| **Дистилляционные таргеты** | НЕТ | таргет должен быть чистым сигналом |

**Почему пол в играющей политике обязателен.** Изначально обоснование было эмпирическим: «если анкер загнать в ноль, он оттуда долго выбирается».

Впоследствии получено формальное подтверждение: **Theorem 1** в Update-Equivalence (Sokota, Farina, Wu, Hu, Wang, Kolter, **Noam Brown**, ICLR 2024) требует буквально, чтобы политика давала *положительную вероятность каждому действию в каждой решающей точке*, иначе гарантии улучшения не существует. Разбор в #109 §3.1.

**Следствие: `sizing_min_prob` не трогать.** Текущий график `0.015 → 0.003` за 50 итераций.

**Отдельно:** `sizing_bucket_min_prob → 0` — это ДРУГОЙ параметр, он снят обоснованно, потому что покрытие стало структурным после введения ветвления по бакетам. Не путать с `sizing_min_prob`.

## 4. Решения по сайзингу, зафиксированные в той же серии отчётов

Не все из §2.6, но утрачены вместе с ним и нужны для контекста.

### 4.1. Ветвление по бакетам

- На raise-узлах ветвимся по **3 бакетам**.
- Внутри бакета: **argmax + 20% случайного выбора** (`sizing_bucket_explore_prob: 0.2`).
- Бакеты — это **только границы** (`sizing_bucket_groups`).
- `bucket_head` — **мёртвая голова**, `weight L2 = 0.000`. Подлежит физическому удалению из `model.py`.

> **2026-08-13:** `sizing_bucket_explore_prob: 0.2` сейчас единственный механизм, дающий редким анкерам визиты (медиана `mask.sum()` = 2, перекос по `anchor_counts` 25×). **Не трогать ни в какую сторону**, пока идут треки.

### 4.2. Симметричный self-play

Одна advantage-сеть и одна sizing-сеть. Внутри итерации копируются во всех 5 оппонентов. Веса обновляются **один раз, между итерациями**. Это требование корректности CFR, а не оптимизация.

### 4.3. Прочее из той же серии

- `sizing_target_top_per_bucket: 5 → 9` (перестало резать анкеры из группы размера 9)
- `sizing_inference_mode` → `hierarchical_rm`
- четыре независимых флага резервуаров
- `warmup_iterations: 100 → 12`
- `sizing_cfr_mode: true` → сайзинг играет **advantage_sizing_net**, а не `sizing_q_net`. То есть плоскость advantage-ноги влияет на силу бота напрямую, а не только на солвер

## 5. Что из #104 впоследствии ОПРОВЕРГНУТО

Чтобы реконструкция не воскресила мёртвые гипотезы:

1. **«12–14 анкеров получают идентичный −ev»** — опровергнуто. Замер внутри состояний: 13.28 **различных** значений из 13.7 доступных. (#107 §2.8)
2. **«Замкнутый круг q_is_ready»** — опровергнут. `anchor_counts` min=496 (iter 5) и min=2748 (iter 10) против порога 128; `q_is_ready = True` с iter 1. (#107 §2.8)
3. **`sign_agreement < 0.5` как признак противоречивости данных** — неверная интерпретация. Метрика измеряла сеть против таргетов, а не шум таргетов. Внутри состояния между визитами **0.556**. (#107 §2.8)
4. **«Маска по q_is_ready» как решение** — выброшено целиком, лечило то, чего нет.
5. **`ptp` как метрика качества sizing-ноги** — отменена. `regret_matching_anchors` инвариантен к равномерному масштабу: сжатие таргетов ×333 даёт `TV = 0.0000` при обвале `ptp`. Действующий гейт — `TV(net) / TV(uniform)` на induced policy. (#107 §2.8 п. 12)
6. **`sizing_anchor_train_steps: 10 → 300` как «главная правка»** — отложено. Симуляция: TV ухудшается 0.449 → 0.53–0.56 во всех вариантах, включая фильтр только-fresh. (#107 §2.8)
7. **`Sizing anchor loss` как индикатор обучения** — бесполезен. `total = fresh_share × fresh_loss`, поэтому падение 0.52 → 0.033 отражает падение доли свежих записей, а `fresh_loss` за 20 итераций **вырос** 0.664 → 0.791. (#107 §2.8 п. 17)
8. **«Резервуар нужен для сбора полного вектора»** — неверно, см. §2.5 ред. 2: накопление живёт в весах через бутстрап.

**Что осталось живым из диагностики:** sizing-нога не лучше равномерного выбора
(`TV(net)/TV(uniform)` = 1.033 для advantage, 1.068 для strategy, без улучшения за 20 итераций);
Q-усадка `std(Q)/std(MC) = 0.189` при `corr = 0.156`; дистилляция теряет 18%; перекос по анкерам
25×; `unaccounted` 39.2% и растёт.

**Ключевой открытый вопрос:** согласованность таргетов с MC-истиной не измерена — таргеты на
12–14 анкерах производны от Q-сети. Разделяет П2 (#107 §6.2).
