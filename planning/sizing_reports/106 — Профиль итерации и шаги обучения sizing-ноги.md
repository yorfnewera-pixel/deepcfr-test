## 0. Профиль итерации: где на самом деле время

```
item                          время      доля
---------------------------------------------
вся итерация                 1013 с      100%
advantage_net (10440 шагов)     64 с        6%
sizing anchors (10 шагов)      ~0 с       ~0%
strategy_net                    ?          ?
обход + eval                  ~900 с      89%
```

**Обучение — 6%.** Гипотеза «дорого обучение на растущем буфере» опровергнута.

```
nodes             2 813 798      узлов на траверс   281
traversals           10 000      max_depth           32
                                 depth_hits           0
```

281 узел на траверс при `max_depth=32` — здоровое дерево. Гипотеза об экспоненте от ветвления по 3 бакетам (`3^k`) **неверна**. `depth_hits = 0` снимает подозрение на баг движка с бесконечным кругом ставок.

```
900 с / 2 813 798 узлов ≈ 320 микросекунд на узел
```

Замедление против прежнего прогона: **0.04 → 0.08 с на игру, ровно вдвое**. Цена узла не менялась — выросло число узлов (возврат `os_force_full_traversal: true` + ветвление по бакетам).

### 0.1. Куда уходят 320 мкс: арифметика бюджета

Eager-вызов PyTorch при `batch=1` тратит **50–100 мкс на диспетчеризацию** (C++/Python bindings, проверки autograd даже под `no_grad()`, аллокация выходного тензора, вызов операторов по одному). Чистая математика на сети 157→256×3 — это ~340 килоFLOP, то есть единицы микросекунд.

Сколько forward-вызовов на узле:

| Тип узла | Вызовы сетей | Оценка диспетчеризации |
|---|---|---|
| hero (534 021) | `advantage_net` + `advantage_sizing_net` (+ `sizing_q_net`) | 150–300 мкс |
| opponent (1 235 913) | `advantage_net` (+ мёртвый q-блок, §1.1) | 50–200 мкс |
| terminal (1 043 864) | 0 (должно быть) | ~0 |

**Вывод: диспетчеризация PyTorch съедает почти весь бюджет узла.** Это меняет приоритеты:

- устранение дублей `encode_state` (§1) даст **меньше**, чем оценивалось в ред. 3
- сокращение **числа forward-вызовов** и снижение цены одного вызова — даст больше

Следствие для §3 (Rust): переписывание обхода не поможет, если время сидит в диспетчеризации тензорной библиотеки, а не в интерпретаторе Python. Условие осмысленности Rust становится строже.

## 1. ПОДТВЕРЖДЁННЫЕ дубли `_encode_state` — править первым

Проверено grep-ом и подтверждено агентом на code-level. Ключ к проблеме — строка 590:

```python
def _encode_state_for_sizing(self, state, player_id):
    if not self.sizing_availability_on_input:
        return self._encode_state(state, player_id)   # ← полный делегат
    base = self._encode_state(state, player_id)
    ...
```

В конфиге `sizing_availability_on_input: false`, поэтому **каждая пара `_encode_state` + `_encode_state_for_sizing` на одном `(state, player)` считает один и тот же вектор дважды**, побитово идентичный.

### 1.1. Мёртвый `q_encoded` при `use_q_baseline: false` — крупнейшая находка

В конфиге `use_q_baseline: false`, но энкод и тензор строятся **до** проверки флага:

| Строка | Что |
|---|---|
| **1440** | `q_encoded = self._encode_state(state, traversing_player)` |
| **2279** | `q_encoded = self._encode_state(state, traversing_player)` (opponent branch) |
| 1965 / 1966 | `next_q_encoded`, `next_policy_encoded` |
| 2353 / 2354 | `next_q_encoded`, `next_policy_encoded` |

Результат используется только внутри `if self.use_q_baseline:`, то есть **никогда** при текущем конфиге.

При 1 235 913 узлах оппонентов это ~1.24 млн лишних энкодов + столько же аллокаций тензоров + **возможно forward `q_net`** — а вот последнее по §0.1 стоит дороже всего остального.

**Правка:** обёртка `if self.use_q_baseline:` вокруг блока целиком (энкод + тензор + forward). Код заведомо мёртвый, результат нигде не читается — риск нулевой.

### 1.2. Пары «encoded_state + sizing_encoded»

| Строки | Контекст |
|---|---|
| **1735 / 1737** | traversing-player ветка |
| **2046 / 2048** | второй traversal-путь |
| **3348 / 3351** | inference / action selection |

Второй вызов возвращает тот же вектор. Считать один раз, переиспользовать.

### 1.3. Третий энкод того же состояния

| Строка | Что |
|---|---|
| **1881** | `_sizing_state_arr = self._encode_state_for_sizing(state, traversing_player)` — тот же узел, что 1735/1737 |
| **2143** | то же для узла 2046/2048 |

Итого на hero-узле энкод считается **три раза** вместо одного. Hero-узлов 534 021.

### 1.4. Четвёртый — внутри `_hierarchical_sizing`

| Строка | Что |
|---|---|
| **1593** | `sizing_encoded = self._encode_state_for_sizing(state, int(state.current_player))` + пересоздание тензора |

Вызывается после того, как энкод уже посчитан выше по стеку, и `state_tensor` уже передан параметром.

**Осторожно:** в коде есть пометка, что убрать этот re-encode пробовали и откатили («сломало обучение, max_depth упал до 10»). Причина была в **размерности** при `sizing_availability_on_input: true` (157 против 187), а не в кэшировании как таком.

→ Править **только внутри ветки `not sizing_availability_on_input`**. Тогда проблема размерности не может возникнуть по построению.

### 1.5. Протокол проверки правок

Правки не меняют вычислений — только не повторяют их. Значит результат обязан совпасть **побитово**.

1. Прогнать 100 траверсов с фиксированным seed **до** правок, сохранить: `Traversal/nodes`, `Loss/Advantage`, содержимое буферов.
2. То же **после** правок.
3. Сравнить. Любое расхождение = где-то энкоды были не идентичны, искать где.

### 1.6. Порядок и ожидания

```
1. §1.1  q_encoded под флаг        ← энкод + тензор + возможный forward, риск нулевой
2. §1.2  пары 1735/1737, 2046/2048, 3348/3351
3. §1.3  третьи энкоды 1881, 2143
4. §1.4  _hierarchical_sizing 1593  ← только в ветке not availability_on_input
```

**Численные оценки выигрыша не доказаны.** Если после всех четырёх правок время упадёт **меньше чем на 15%** — значит `encode_state` не был узким местом (что по §0.1 вполне вероятно), и дальше §4.7.

## 2. Почему оригинал `dberweger2017` работал «за секунды»

Не оптимизация кода, а **в 30–100 раз меньше работы**.

| | dberweger2017 | текущая версия |
|---|---|---|
| Действий | **3** | **4** |
| Сайзинг | **1 скаляр** из regression-головы | **15 анкеров, ветвление по 3 бакетам** |

| Сетей на узле героя | 1 | до 3 |

1.24 млн узлов оппонентов в оригинале стоили бы почти ноль. Скалярный сайзинг из regression-головы — ровно то, от чего проект ушёл в #50.

**Сравнение по времени некорректно.**

## 3. Rust: не сейчас, и условие стало строже

Обход на Rust ускорит **питоновскую обвязку**, но forward всё равно пойдёт через тензорную библиотеку — те же умножения, та же диспетчеризация на `batch=1`.

Цена: месяцы работы, потеря диагностики (`relapse_diff`, `checkpoint_tools`, шесть `diagnose_*`), риск расхождений в CFR-логике.

**Условие осмысленности (уточнено по §0.1):** Rust помогает, только если доминирует **интерпретатор Python** (обход, циклы, `encode_state`). Если доминирует **диспетчеризация тензорной библиотеки** — Rust не помогает, потому что та же диспетчеризация никуда не денется. В этом случае решение — §4.7 (другой рантайм инференса) или §4.8 (меньше вызовов).

**Сначала §1 и замер.**

## 4. Почему «статичные оппоненты» думают долго

Заморозка весов не делает вызов дешёвым — цена в **накладных расходах на вызов**:

```python
encode_state(...)                     # 157 float, циклы по игрокам, canonical suit map
torch.from_numpy(...).unsqueeze(0)    # аллокация
net(tensor)                           # forward batch=1 → диспетчеризация 8 слоёв
.cpu().numpy()                        # обратно
regret matching в numpy               # ещё аллокации
```

### 4.1. Замер разбивки

Инструментировать таймерами: `encode_state` / `net forward` / `apply_action` / `_resolve_effective_sizing` / буферы / прочее. На **100 траверсах**, печатать раз в итерацию.

Альтернатива быстрее: `cProfile` + сортировка по `tottime` (не `cumulative` — покажет, где реально жжётся CPU, а не что глубоко в стеке).

### 4.2. Кэш политики оппонентов — вероятно бесполезен

Требует повторяющихся энкодов. Энкод оппонента включает **его карты**, а карты в каждой раздаче новые. При 10 000 траверсов с разными сидами повторов почти наверняка мало.

Проверяется дёшево: счётчик уникальных ключей против общего числа вызовов. Уникальных 90%+ → бесполезен.

**Понижен в приоритете** относительно ред. 2.

### 4.3. Инкрементальный энкод — сложнее, чем казалось

В `encode_state` есть `_build_suit_canonical_map` (канонизация мастей пересчитывается от карт целиком) и нормировочный делитель, зависящий от банка. «Поправить 3–5 полей» не выйдет.

**Понижен в приоритете.** Рассматривать только если §1 не помог и замер показал доминирование энкода.

### 4.4. Терминалы: 37% узлов

`terminal = 1 043 864` — сеть не нужна. Проверить, что в терминальной ветке нет лишнего энкода или обращения к сетям.

### 4.5. Eval внутри 900 секунд

В логе не выделен отдельной строкой. 500 игр × ~50 решений = 25 тыс. forward-ов с `batch=1`. Замерить отдельно.

### 4.6. Чего НЕ делать

- **батчинг обхода** (BFS вместо DFS): ломает детерминизм, нужный S2-харнессу
- **GPU**: PyTorch собран как `2.11.0+cpu`; при `batch=1` не помог бы
- `pin_memory` / `non_blocking`: лечат пропускную способность, а проблема — латентность
- **обновление версии PyTorch**: `2.11.0` уже новее всех веток, где появились `cpp_wrapper` и улучшения CPU-инференса. Апгрейда не требуется, а трогать версию посреди работающего прогона — риск для сериализации чекпоинтов и поведения оптимизаторов

### 4.7. Рантайм инференса: ONNX Runtime предпочтительнее `torch.compile`

Если замер покажет доминирование forward-диспетчеризации, а не энкода:

| Вариант | Плюсы | Минусы |
|---|---|---|
| **ONNX Runtime** | скомпилирован под C++ инференс, не тащит autograd; на мелких сетях с `batch=1` обычно 2–5× быстрее eager | нужен экспорт замороженной копии в начале каждой итерации |
| `torch.compile` | 2–3 строки кода | **компилирует при первом вызове** (секунды); веса меняются каждую итерацию → либо перекомпиляция ×300, либо разбираться с кэшированием графа |
| LibTorch / TorchScript C++ | предсказуемо | много обвязки |

**Почему ONNX первым:** граф статичный, веса подставляются, поведение предсказуемое. `torch.compile` требует выяснить, кэшируется ли граф при смене весов той же формы — иначе на 300 итерациях перекомпиляция съест выигрыш.

**Если всё же `torch.compile`:** брать `mode="reduce-overhead"` или дефолт. **Не** `max-autotune` — он перебирает варианты ядер и компилируется в разы дольше; придуман для больших GPU-моделей.

В любом случае: экспорт/компиляция делается **один раз за итерацию** для замороженных копий, и её стоимость надо замерить отдельно.

**Обязательная проверка:** численная идентичность выхода нового рантайма и eager PyTorch на наборе состояний. Расхождение в последних знаках допустимо, но должно быть проверено, а не предположено.

### 4.8. Сократить число forward-вызовов на hero-узле

По §0.1 это направление с наибольшей отдачей.

На hero-узле вызываются `advantage_net` и `advantage_sizing_net` **с одним и тем же входом** (157 float при `sizing_availability_on_input: false`). Это два отдельных eager-вызова, то есть двойная диспетчеризация.

Варианты:

1. **Проверить, нужны ли обе на каждом узле.** `advantage_sizing_net` нужна только если raise легален. Если сейчас вызывается безусловно — это чистая экономия.
2. **Объединить в один вызов**: прогнать batch из 2 копий входа через объединённую сеть, либо склеить головы. Требует правки `model.py`, но убирает половину диспетчеризации на hero-узлах.
3. **`sizing_q_net`**: проверить, вызывается ли она в дополнение к `advantage_sizing_net` или вместо. Если в дополнение — третий вызов на том же узле.

## 5. Эпохи против шагов: две разные схемы

### Что такое эпоха и зачем их 20

Одна эпоха = один проход по буферу. Но проход **не значит «выучила»**: шаги маленькие (`lr = 1e-4`), за один проход сеть сдвигается в нужную сторону, но не доходит до минимума. Двадцать эпох = двадцать проходов до сходимости.

### Асимметрия: 10 440 против 10

```
advantage:  534 021 / 1024 = 522 минибатча × 20 эпох = 10 440 шагов, каждый сэмпл ×20
sizing:     sizing_anchor_train_steps_per_iteration = 10 шагов, ~1% буфера, ×1
```

**Разница в 1044 раза.** Sizing-нога устроена как в оригинале (`epochs=3` = 3 минибатча), advantage — по-современному.

### Следствие: «сеть не различает борды» — не загадка

За 15 итераций sizing-нога сделала **150 шагов** (advantage — 156 600). При `bias = constant_(0.01)` и нулевых весах выходного слоя она обязана быть почти константой. Это арифметика, а не диагноз.

Отсюда наблюдения из [#104 §0](104-S6-sizing-advantage-targets-fix.md) объясняются проще, чем «таргеты не являются функцией состояния»:

- `pearson ≈ 0.026` — сеть не начала учиться
- `corr(anchor_head.bias, per_anchor_target_mean) = 0.60 → 0.73` — выучены только маргиналы; это первое, что выучивает регрессия
- `top-1: 0.521 → 0.548 → 0.573` растёт, а Pearson стоит → уточняется **маргинальный** порядок анкеров, state-специфичности в этом нет (Pearson инвариантен к масштабу, при state-зависимом ранжировании он бы рос вместе с top-1)

### Правка

```yaml
sizing_anchor_train_steps_per_iteration: 10 → 300
strategy_sizing_train_steps: 40 → 300
```

300 × 1024 ≈ 307 тыс. сэмплов ≈ 30% буфера. Advantage-нога делает 10 440 шагов за 64 с (~6 мс/шаг) → 300 шагов sizing ≈ **2 с** на фоне 1013.

`strategy_sizing_train_steps` тоже: иначе `strategy_sizing_net` отстанет, а именно её читают солвер и multiboard-гейт.

### Про «увеличивать steps рискованно»

Риск ровно один — переобучение на резервуарный буфер. Он **измеряется**, а не угадывается: отложить 10% буфера как holdout, считать лосс на train и на holdout. Расходятся → переобучение; идут вместе → недофит, можно ещё. ~15 строк.

При 150 шагах на миллион записей разговор о переобучении преждевременен на несколько порядков.

## 6. Метрики диагностики: что починить

### 6.1. `std(logit)/std(target)` больше не информативен

Таргеты сжались в 7.5 раз после клипа IW (RMSE 6.32 → 0.845), логиты почти не двигались. Отношение двух малых чисел, одно из которых ≈ 0, ничего не говорит. Прежний ориентир `1/86` несравним с текущими `10⁻⁴–10⁻³`.

**Заменить на:** std логита по сэмплам для **фиксированного анкера**. Взять анкер k, прогнать 10 000 разных состояний, посмотреть разброс выхода. Однозначно отвечает «константа или нет» без нормировки.

### 6.2. Cross-board ratio нестабилен — убрать из решающих

```
iter 5:  0.862
iter 10: 2.017
iter 15: 1.307
```

Значения **> 1** означают, что соседи по энкоду разнороднее случайных пар — бессмыслица для любого реального сигнала. Скачок 0.86 → 2.0 → 1.3 за 10 итераций = шум (24 борда, 8 соседей — слишком мало проб).

Решения по этой метрике не принимать, пока не стабилизирована.

### 6.3. Чего в отчётах нет

- метрик `strategy_sizing_net` — а её читают солвер и multiboard-гейт
- `std(logit)` и `std(target)` явными числами (сейчас восстанавливаются через slope × pearson)
- фактических train steps, loss и норм обновлений `advantage_sizing_net` — чтобы подтвердить, что 300 шагов реально применились

## 7. Открытый вопрос: какая нога реально играет сайзинг

В примечании агента: sizing-решения могут фактически идти через `sizing_q_net`, а не `advantage_sizing_net`.

**Если так, плоскость advantage-ноги не влияет на игру вообще** — она портит только дистилляцию (`strategy_sizing_net`) и абстракцию солвера.

Это меняет приоритет S6: починка нужна для солвера, но не для силы бота.

**Проверяется чтением одной развилки** в `cfr_traverse_multi`. Сделать это **до** поднятия train steps: ответ может обесценить всю ветку.

Заодно этот же ответ нужен для §4.8: вызываются ли обе sizing-сети на одном узле или одна вместо другой.
