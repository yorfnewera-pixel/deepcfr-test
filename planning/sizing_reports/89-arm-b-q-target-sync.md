## Краткое описание

Arm B' — диагностический зонд из плана #88: гипотеза «обрыв на iter 100 вызван `q_target_update_interval=100`». Референс (`DeepPDCFR-master`, `QValueTrainer.train_model`) синкает Q-target каждые 50 train-шагов внутри итерации на свеже-инициализированной сети. Проектная заморозка на 100 CFR-итераций создаёт ступеньку: первый синк только на iter 100, до этого `q_target_net.q_head = zero-init` (#74-v6).

Arm B': `q_target_update_interval: 100 → 10` (одна переменная, config.yaml). Ожидание: M0 — нет ступеньки, raise_freq(200) ≥ 30%.

**Результат: FAIL. Поведение полностью идентично baseline (test88seed1, sync=100).** Relapse не вызван sync-интервалом.

## Анализ: почему sync-интервал не влияет

### Гипотеза до прогона
Проектный `q_target_update_interval=100` создаёт ступеньку: первый синк на iter 100. До этого `q_target_net` = zero-init → TD-bootstrap через мёртвую сеть → advantage-цели зашумлены → advantage-flip ускоряется.

### Данные после прогона
1. **На iter 100 поведение идентично.** Оба (sync=100 и sync=10) показывают OK: raise 40.7-40.8%, win 42.2-42.8%. «Ступенька» не проявляется в метриках — advantage-сеть компенсирует шумный bootstrap на ранних итерациях.
2. **Регрессия на iter 200 идентична.** Оба коллапсируют в 0.10 с raise ~16-18%. `next_strategy_raise_mass` падает с 0.37 до 0.38 (sync=100) / 0.38 (sync=10) — идентично.
3. **Траектория 200→400 идентична.** Полный коллапс к iter 300 (raise 0.2% на fixed-state), частичное восстановление к 400.

### Интерпретация
`q_target_update_interval` не является rate-limiting фактором relapse. Даже с sync=1 (который эквивалентен использованию online-сети — нестабильный, но «живой» таргет) картина не меняется vs sync=10. Это означает, что **проблема не в том, насколько свежий target**, а в том, что **Q-сеть структурно не может обучиться prefer raise > fold** из-за reward-grounding asymmetry (#81).

Косвенно это подтверждает правоту Opus: «Arm B — дешёвый диагностический зонд, не фикс. Настоящий референс — Arm C (refit с нуля).»

### Q-сеть: стабильная, но бесполезная для raise
```
q_net[Raise] < q_net[Fold] в 67-88% состояний на ВСЕХ итерациях
```
Q-сеть всегда считает fold лучше raise. Advantage-сеть на iter 100 компенсирует это (adv_raise = +0.64 > adv_fold = −5.10), но к iter 200-300 компенсация ломается (H3 — накопление regret). Свежесть target-сети не меняет этот фундаментальный дисбаланс.

## Следствия для дерева решений #88

Дерево из плана #88:
```
B' (sync=10), iter 400
├── M0 FAIL → обрыв не от sync-режима → возврат к diff, копать advantage-сторону  ← МЫ ЗДЕСЬ
├── M0+M1 PASS, M2 FAIL → Arm C (refit)
└── M0+M1+M2 PASS → Arm A (Polyak)
```

**Следующий шаг: Arm C — refit Q с нуля каждую итерацию + best-model**, по образцу `QValueTrainer.train_model` из референса. Это истинный референсный режим: свежая сеть каждый iter, target sync каждые 50 train-шагов, восстановление best-model в конце итерации.

Ключевое отличие от B': refit пересоздаёт **всю Q-сеть с нуля** (новые веса, новый Adam), а не только частоту синка. Это убирает накопление багов от предыдущих итераций и даёт честный фит на свежих данных.
