# Bug #68: Диагностика Target Formation в SizingQBuffer

## Статус: FIXED (Instrumentation)

## Описание

После #67 sizing политика временно улучшилась (iter300 — лучший чекпоинт), но к iter400/500
relapse назад в collapse 0.10. Причина relapse неизвестна:

- `+5.0` выброс в `mean_target_by_source_anchor` — баг scale/normalization или реальный редкий outcome?
- `source2` lookahead плоский по анкорам — не несёт sizing-сигнала?
- `source0` on-policy снова вытесняет остальные данные в buffer?

Без диагностики target formation следующий фикс — гадание.

Добавлена **read-only instrumentation**: запись pre-clip и post-clip target values
при каждой записи в `SizingQBuffer`, агрегация по `(source, anchor_idx)` и вывод в чекпоинт-отчёт.

## Изменения

### 1. Новые методы

**Файл:** `src/core/deep_cfr.py`

`_compute_sizing_q_target_values(raw_v3, pot)` — возвращает `(pre_clip_target, post_clip_target)`:

```python
def _compute_sizing_q_target_values(self, raw_v3, pot):
    pot_val = max(float(pot), 1.0)
    pre_clip = float(raw_v3) / pot_val  # или raw
    post_clip = float(np.clip(pre_clip, -5.0, 5.0))
    return pre_clip, post_clip
```

`_normalize_sizing_q_target` теперь делегирует этому методу (signature не менялась).

`_record_sizing_q_target_diag(source, anchor_idx, raw_v3, pot, pre_clip_target, post_clip_target)` —
накапливает per (source, anchor_idx) статистику:

```text
count, clip_high, clip_low, raw_min/max, pre_min/max, post_min/max
```

При `sizing_q_target_diagnostics_enabled=False` — no-op.

### 2. Точки записи диагностики

Вставлено в 3 call sites:

| Source | Где | Что пишет |
|--------|-----|-----------|
| 0 | `cfr_traverse_multi` OS node, реальный raise | `sizing_regret + ev_hat` → /pot → clip |
| 1 | `cfr_traverse_multi` OS node, probe sizing | то же с `is_probe=True` |
| 2 | `_perform_sizing_lookahead` | `v_k` (bootstrap или terminal) → /pot → clip |

### 3. Чекпоинт

**Файл:** `src/core/deep_cfr.py`

`_build_checkpoint` сохраняет `sizing_q_target_diag` если флаг включён и данные есть.
`_load_checkpoint` восстанавливает его из чекпоинта.

### 4. Отчёт

**Файл:** `tools/checkpoint_tools.py`

Новые функции `run_sizing_q_target_diag_stats` / `print_sizing_q_target_diag`.

Формат в JSON:

```json

```

## Вопросы к прогону после патча

После прогона с диагностикой (с нуля до 200+):

1. Где бьёт clip `±5.0`? Только source0 или все source?
2. При каких `count`? Одиночные `count=1` или массово?
3. `source2_flatness.anchor_pre_range_mean` — близок к 0 (плоский) или > 0 (различает)?
4. `pre_clip_target` у source2 того же порядка, что у source0, или на 1-2 порядка меньше?

## Decision tree

```text
clip_high массово у source0, никогда у source2
→ scale/normalization mismatch — фиксить единицы source0

clip_high редко, count=1 у всех source
→ не root cause, искать дальше

source2_flatness ≈ 0
→ lookahead не различает anchors — фиксить source2/lookahead

source0 buffer доля снова > 60%
→ replay isolation / admission control
```

## Что не трогалось

- Обучение, loss, inference — без изменений
- SizingQBuffer admission — без изменений
- Target значения — без изменений (только запись pre/post)
- eps, min_prob, temperature — без изменений

## Фаза 0 (дополнение): Инструментация отката + Regression Guards

### Что добавлено

После прогона с Фазой 0 выяснилось, что `sizing_q_target_diag` не попадал в обычные
`_full_report.json` — только в `_diagnose_report.json` через режим `--mode diagnose`.
Добавлено три улучшения:

#### 1. `sizing_q_target_diag` в full reports

**Файл:** `tools/checkpoint_tools.py` — `save_json_report`

Теперь `sizing_q_target_diag` пишется и в обычные `_full_report.json`:

```python
sqtd = result.get('sizing_q_target_diag')
if sqtd is not None:
    report['sizing_q_target_diag'] = sqtd
```

#### 2. Low-count amplification risk

**Файл:** `tools/checkpoint_tools.py` — `run_sizing_q_target_diag_stats`

Добавлены метрики:

```json
"low_count_cells": ["0:14", "1:13", ...],
"single_anchor_dominance_pct": 78.3,
"single_anchor_dominance_anchor": 0.10,
"amplification_risk": true
```

- `low_count_cells` — ячейки где count < 5 (шум, который стратифицированный sampling из #67 амплифицирует)
- `single_anchor_dominance` — если один анкор > 60% всех записей

**Файл:** `tools/checkpoint_tools.py` — `compute_verdict`

Добавлен чек single anchor dominance на уровне играемой sizing-статистики:

```python
if cnt / total_sizings > 0.60:

```

Теперь verdict `WARN` сработает, если любой анкор занимает >60% сыгранных sizing.

## Фаза 0 — Hotfix: `load_full_checkpoint` не читал `sizing_q_target_diag`

### Статус: FIXED

### Корень

`_build_checkpoint` (deep_cfr.py:2644-2648) корректно сохраняет `sizing_q_target_diag`
в `.pt` файл при `sizing_q_target_diagnostics_enabled=True`. Но `load_full_checkpoint`
в `tools/checkpoint_tools.py` (стр. 245-248) загружал `sizing_q_buffer_sources`,
`_anchor_indices`, `_targets`, но **не загружал** `sizing_q_target_diag`.

Цепочка:

```text
_build_checkpoint → .pt (✅ запись есть)
load_full_checkpoint → nets (❌ ключ не читается)
run_sizing_q_target_diag_stats → nets.get() → None → return None
save_json_report → поле пропускается
```

Именно поэтому во всех `multi_new/*_full_report.json` поле `sizing_q_target_diag`
отсутствовало, хотя код записи и конфиг были активированы.

### Фикс

**Файл:** `tools/checkpoint_tools.py` — `load_full_checkpoint`, стр. 249

Добавлено:

```python
if 'sizing_q_target_diag' in ckpt:
    nets['sizing_q_target_diag'] = ckpt['sizing_q_target_diag']
```

Теперь при следующем прогоне `_full_report.json` будет содержать полную диагностику #68.

### Тесты

38/38 passed без изменений.
