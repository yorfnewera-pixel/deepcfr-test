# Задача 1. Добавить прямую диагностику diversity

## Цель

Измерять фактическую уникальность частиц, а не пытаться выводить её из одного значения ESS.

Текущий `belief_ess` в `beliefs.py` является ESS финальных proposal weights после последнего учтённого решения. Он не показывает напрямую:

- сколько уникальных particles пережило resampling;
- сколько уникальных particles попало в финальный draw;
- сколько уникальных particles попало в будущий holdout;
- сколько раз одна и та же hidden history повторяется.

## Файлы

Изменить:

- `src/runtime_search/beliefs.py`
- `src/runtime_search/policy.py`
- `src/runtime_search/paired_evaluation.py`

Тесты:

- `tests/test_runtime_search_beliefs.py`
- `tests/test_runtime_search_policy.py`

## Изменение модели данных

Добавить в `ReachWeightedBeliefs` диагностические поля:

```python
proposal_unique_count: int
selected_unique_count: int
selected_duplicate_count: int
selected_duplicate_fraction: float
```

Если holdout будет формироваться внутри sampler-а, добавить:

```python

holdout_duplicate_count: int | None
holdout_duplicate_fraction: float | None
```

Предпочтительно не помещать holdout-specific поля в общий sampler, если holdout будет отдельной функцией. В этом случае достаточно:

```python

    total_count: int
    unique_count: int
    duplicate_count: int
    duplicate_fraction: float
```

и хранить два объекта:

```python
selected_diversity: ParticleDiversity
proposal_diversity: ParticleDiversity
```

## Ключ particle

Уникальность считать по полному hidden history:

```text
(
    opponent hand 0,
    opponent hand 1,
    ...,
    opponent hand N,
    runout cards in order,
)
```

Для карт использовать существующий `card_key()` из `src/runtime_search/cards.py`.

Не использовать только hands или только runout: одинаковые руки с разным runout являются разными particle histories.

Добавить небольшой helper:

```python
def particle_key(particle: BeliefParticle) -> tuple:
    return (
        tuple(
            tuple(card_key(card) for card in hand)
            for hand in particle.opponent_hands
        ),
        tuple(card_key(card) for card in particle.runout),
    )
```

Для любой последовательности particles:

```python
def particle_diversity(
    particles: Sequence[BeliefParticle],
) -> ParticleDiversity:
    keys = [particle_key(particle) for particle in particles]
    unique_count = len(set(keys))
    total_count = len(keys)
    duplicate_count = total_count - unique_count
    return ParticleDiversity(
        total_count=total_count,
        unique_count=unique_count,
        duplicate_count=duplicate_count,
        duplicate_fraction=(
            duplicate_count / total_count if total_count else 0.0
        ),
    )
```

Не считать одинаковые Python object identity. Сравнивать нужно именно содержимое hidden history.

## Тесты

Добавить тесты:

1. Все разные particles дают `unique_count == total_count`.
2. Две particles с одинаковыми hands и runout считаются одной unique history.
3. Разный порядок runout считается разной history.
4. Разные opponent hands считаются разными history.
5. Пустая последовательность не вызывает деление на ноль.
6. Resampling с контролируемым RNG действительно может вернуть duplicates.
7. Diversity финально выбранных particles сохраняется в результате sampler-а.

# Задача 4. Спроектировать локальный holdout без leakage

## Основной estimand

Для каждого root измерять не EV целой раздачи, а локальный эффект изменения root policy:

```text
local_delta =
    E_holdout[Q_holdout · (pi_search - pi_blueprint)]
```

где:

- `Q_holdout[a]` оценивается на свежих holdout particles;
- `pi_blueprint` это root prior;
- `pi_search` это policy после MMDS;
- все root actions оцениваются на общих holdout histories/runouts.

Это предпочтительнее одиночного сравнения sampled action, потому что не добавляет лишнюю дисперсию от финального сэмплирования действия.

Дополнительно можно хранить:

```text
sampled_action_delta =
    Q_holdout[sampled_search_action]
    - Q_holdout[sampled_blueprint_action]
```

Но primary metric должна быть policy-level delta.

## Трёхчастное разделение

Для каждого root нужны три логически независимые роли:

```text
Part A: выбор пары best/runner-up или диагностического root signal
Part B: оценка mc_values и построение MMDS policy
Part C: свежий holdout для измерения local_delta
```

`Part C` не должна использоваться для:

- выбора best action;
- выбора runner-up;
- noise gate;
- MMDS update;
- выбора конфигурации;
- выбора strata post hoc.

## Размер

При текущих `128` particles:

```text
примерно 42 / 42 / 44
```

Это слишком мало для основного результата.

Для первого рабочего локального эксперимента использовать:

```text
belief_particles = 384
```

Минимальный fallback:

```text
belief_particles = 256
```

Целевой параметр должен быть конфигурируемым:

```python
local_holdout_particles: int = 128
local_selection_particles: int = 128
local_update_particles: int = 128
```

или единый:

```python
local_particles_per_partition: int = 128
```

Начать с равных частей. Не подбирать размер после просмотра результата.

# Задача 5. Реализовать holdout particles без duplicates

## Требование

Holdout должен быть сформирован так, чтобы одна и та же hidden history не учитывалась несколько раз в расчёте standard error.

Простое `rng.choice(..., replace=True)` для holdout запрещено.

## Предпочтительная реализация

1. Сгенерировать weighted proposal set.
2. После финального weighting агрегировать одинаковые particle keys.
3. Для каждого unique key получить суммарный вес.
4. Выбрать holdout без replacement из unique histories.
5. Нормализовать веса или использовать selected unique particles как равновесную empirical sample, но явно задокументировать estimand.
6. Если unique histories меньше требуемого holdout size, вернуть diagnostic flag и не считать обычный iid `z-score`.

Важно: нельзя просто удалить duplicates после reward calculation. Удаление должно происходить до rollout evaluation.

Добавить helper:

```python
def select_unique_particles(
    particles: Sequence[BeliefParticle],
    *,
    count: int,
    rng: np.random.Generator,
) -> tuple[BeliefParticle, ...]:
    ...
```

Если weighted selection без replacement окажется статистически сложной, первая версия должна использовать независимый uniform blocker-aware sampler для holdout, отдельно от reach-weighted selection. Но это нужно явно обозначить:

```text
selection/update beliefs = reach-weighted
holdout beliefs = fresh blocker-aware posterior approximation
```

Лучше сначала реализовать корректный holdout с прозрачным estimand, чем использовать псевдо-independent resampled particles и считать обычный SE.

## Тесты

Добавить:

1. Holdout никогда не содержит повторяющиеся `particle_key`.
2. Selection/update particles не попадают в holdout по key, если требуется disjoint split.
3. При недостатке unique histories возвращается диагностический флаг.
4. Повторный запуск с тем же seed воспроизводим.
5. Разные seeds дают разные holdout, но legal/valid histories.
6. Все holdout particles не содержат duplicate cards.

# Задача 6. Реализовать локальную оценку root policy

## Файлы

Предпочтительно создать:

- `src/runtime_search/local_evaluation.py`

Изменить:

- `src/runtime_search/policy.py`
- `src/runtime_search/paired_evaluation.py` только для общей сериализации, если потребуется.

Тесты:

- `tests/test_runtime_search_local_evaluation.py`

## API

Создать результат:

```python
@dataclass(frozen=True)
class LocalRootEvaluation:
    action_values: np.ndarray
    blueprint_expected_value: float
    search_expected_value: float
    local_delta: float
    local_delta_se: float
    local_delta_zscore: float
    holdout_count: int
    holdout_unique_count: int
    diagnostic_flags: tuple[str, ...]
```

Функция должна иметь контракт примерно такого вида:

```python
def evaluate_root_policy_holdout(
    state: pkrs.State,
    *,
    hero_id: int,
    root_actions: Sequence[pkrs.Action],
    blueprint_policy: np.ndarray,
    search_policy: np.ndarray,
    holdout_particles: Sequence[BeliefParticle],
    continuation_policy: BatchContinuationPolicy,
    rng: np.random.Generator,
    max_depth: int,
) -> LocalRootEvaluation:
    ...
```

## Rollout logic

Для всех holdout particles:

- один hidden history/runout на particle;
- все root actions на общей particle;
- continuation policy одинаковая;
- reward matrix имеет форму:

```text
[num_holdout_particles, num_root_actions]
```

Для каждой particle:

```python
blueprint_value = dot(blueprint_policy[root_slots], rewards)
search_value = dot(search_policy[root_slots], rewards)
difference = search_value - blueprint_value
```

Затем:

```python
local_delta = mean(differences)
local_delta_se = std(differences, ddof=1) / sqrt(n)
local_delta_zscore = local_delta / local_delta_se
```

Если holdout particles дедуплицированы и являются неравномерно взвешенными, обычный iid SE использовать нельзя. Для первой версии выбрать один из двух явных режимов:

```text
mode A: unique holdout particles treated as empirical unweighted sample
mode B: weighted estimator with weighted variance and effective sample size
```

Рекомендуемый первый вариант: `mode A`, но в отчёте указывать, что estimand является empirical mean по unique holdout histories.

## Тесты

Синтетические reward matrices:

1. Одинаковые policies дают `local_delta == 0`.
2. Policy с большей вероятностью лучшего action даёт положительный delta.
3. Общие rewards для всех actions соблюдают CRN.
4. Перестановка action slots с соответствующей перестановкой policy не меняет delta.
5. Holdout duplicates не проходят в основной evaluator.
6. Нулевая дисперсия даёт `z = inf` только если delta ненулевой; при delta `0` должен быть `0`.
7. Некорректные policy shapes и non-finite values отклоняются.

Команда:

```powershell
python -m pytest tests/test_runtime_search_local_evaluation.py -q
```

# Задача 9. Агрегация локальных результатов

## До запуска зафиксировать estimand

Основной агрегат:

```text
mean local_delta по root observations
```

Но roots могут иметь разный экономический масштаб. Поэтому сохранить два агрегата:

1. Unweighted root mean:

```text
mean(delta_root)
```

2. Pot-normalized root mean:

```text
mean(delta_root / value_scale_root)
```

Не смешивать их в один показатель.

Дополнительно:

- median delta;
- доля roots с `delta > 0`;
- доля roots с `z > 1.96`;
- доля roots с `z > 2`;
- median/p90 `local_delta_se`;
- median/p90 holdout unique count;
- bootstrap CI по roots;
- отдельные results по stage и prior stratum.

## Единица независимости

Root observations, происходящие из одной раздачи или одного constructed spot, могут быть зависимыми. Поэтому:

- основной CI считать cluster bootstrap по `seed/spot`, а не bootstrap по отдельным particle rewards;
- particle-level SE использовать только как внут(root)-диагностику;
- в отчёте явно различать:
  - `within_root_holdout_se`;
  - `between_root bootstrap CI`.

# Задача 10. Стратификация по `prior_log_ratio`

## Использовать фиксированные границы

Для первого отчёта:

```text
[0, 5)
[5, 15)
[15, 40)
[40, +inf)
```

Причина: границы связаны с требуемым normalized gap:

```text
need = prior_log_ratio / eta_effective
```

При `eta_effective = 6.6667`:

```text
[0, 5)   -> need < 0.75
[5, 15)  -> need 0.75..2.25
[15, 40) -> need 2.25..6.0
[40, inf) -> need >= 6.0
```

Добавить отдельную категорию:

```text
prior_log_ratio approximately zero
```

Например:

```python
tie_epsilon = 1e-9
```

Но не считать `prior_log_ratio == 0` автоматически доказанной ничьей во всех случаях. Нужно также сохранить:

- top prior values;
- second prior values;
- legal action count;
- whether the top prior slots are tied within a numerical tolerance.

## Для каждой страты публиковать

- coverage среди всех roots;
- coverage среди active roots;
- количество roots;
- median `prior_log_ratio`;
- median `need`;
- median `mc_gap`;
- median local delta;
- долю positive local delta;
- median local z-score;
- policy L1;
- policy argmax changes;
- action changes;
- holdout unique count;
- bootstrap CI.

Квантили можно добавить только как вспомогательную таблицу. Не использовать их вместо фиксированных границ, чтобы результаты разных checkpoint-ов были сопоставимы.

# Задача 11. Критерии принятия решения

## Локальный тест считается информативным, если

- holdout не использовался при выборе search policy;
- holdout histories уникальны или применяется явно описанная weighted variance;
- для большинства roots есть минимум заранее заданного числа unique holdout histories;
- есть результаты минимум по двум независимым seed groups;
- нет систематического rollout failure;
- CI рассчитан на уровне roots/clusters, а не только particles.

## Гейт для перехода к глобальному EV

Не требовать положительного результата в каждом отдельном root.

Переходить к следующему этапу только если одновременно выполнены условия:

1. Overall local delta положителен.
2. CI для cluster bootstrap не полностью отрицателен.
3. Хотя бы одна из двух основных strata с умеренным prior gap показывает устойчиво положительный результат.
4. High-prior strata не маскируют результат искусственным отбором.
5. При дедупликации holdout знак эффекта не меняется.
6. Результат воспроизводится минимум на двух независимых seed subsets.
7. Оценён ожидаемый effect size для глобального EV.

Если local delta около нуля или отрицателен, глобальный EV не запускать.

## Ожидаемый итог

Агент должен закончить не изменением параметров solver-а, а одним из трёх чётких выводов:

1. **Локальное улучшение подтверждено.** Тогда оценить effect size и спланировать глобальный EV с заранее рассчитанным числом samples.
2. **Локального улучшения нет.** Глобальный EV не запускать, исследовать качество MMDS/continuation policy или blueprint.
3. **Результат искажён diversity/holdout-проблемой.** Сначала исправить sampling и повторить локальный тест.

`max_prior_log_ratio` до этого этапа не вводить в рабочую конфигурацию. Использовать только для стратификации и оценки coverage.
