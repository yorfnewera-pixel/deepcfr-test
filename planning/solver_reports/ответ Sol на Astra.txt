Astra здесь в основном права. Моя формулировка **«нынешнее направление оптимальнее всех» была слишком категоричной**. Корректнее сказать:

> **MMDS — разумная и экономичная первая гипотеза для локального postflop-улучшения blueprint, но пока не доказано, что это сильный или безопасный subgame solver.**
> 

## Главное уточнение терминологии

Текущая система делает:

```
текущий infoset
→ belief по скрытым рукам
→ оценивает каждое root-действие полными доигрываниями
→ делает один MMDS update
→ дальше оба игрока снова следуют frozen blueprint
```

Поэтому она:

- учитывает будущие улицы и ставки через rollouts;
- может улучшить текущее решение против моделируемого соперника;
- но **не пересчитывает стратегии будущих infoset**;
- не ищет равновесие всей подыгры;
- не обеспечивает автоматически снижение exploitability.

Технически точнее называть это:

- `root policy improvement`;
- `decision-time local search`;
- `one-step MMDS policy improvement`;

а не полноценным `subgame solver`.

# Где Astra особенно права

## 1. Boundary value network сейчас не обязательна

Я слишком рано поставил её в обязательный следующий этап.

Если rollout действительно доходит до терминала, получаем настоящий игровой payoff. Если поиск прерывается и система возвращается к blueprint, отдельная value network для текущего root-only варианта необязательна.

Она понадобится, когда появится одно из условий:

- rollout принудительно обрезается до терминала;
- добавляется более глубокое ветвление будущих решений;
- полный rollout не помещается в latency budget;
- требуется резко увеличить число particles/runouts;
- начинается ReBeL/DeepStack-подобный depth-limited search.

Правильная последовательность:

```
сначала terminal rollouts
→ проверить, хватает ли времени
→ только при необходимости learned boundary value
```

## 2. Update-equivalence не гарантирует улучшение

Update-equivalence означает примерно следующее:

> При корректном sampling и бесконечном количестве samples оценённый update совпадёт с update исходного алгоритма.
> 

Но это ещё не означает:

```
один update → обязательно лучшая стратегия
```

Тем более в реальной реализации присутствуют:

- конечное число particles;
- шум Q-оценок;
- ошибочный belief;
- action abstraction;
- приблизительный blueprint;
- выбор гиперпараметров MMDS;
- возможный selection bias после выбора лучшего действия;
- отличие реального соперника от frozen blueprint.

Поэтому MMDS надо оценивать эмпирически, а не считать доказанно улучшающим poker policy.

## 3. EV против blueprint не равно exploitability

Если runtime search выигрывает у фиксированного blueprint, доказано только:

```
candidate лучше в этом конкретном matchup
```

Это не доказывает, что candidate:

- менее эксплуатируем;
- лучше против неизвестного соперника;
- лучше против best response;
- безопаснее исходного blueprint.

Более того, локальная адаптация может повысить EV против одного opponent model и одновременно открыть сильную эксплуатацию другим соперником.

# Практические проблемы действительно важнее новых статей

## 1. Разная семантика blueprint — потенциально критическая ошибка

Если `policy_runtime` делает:

```
p(a) < 0.05 → удалить
→ перенормировать
```

а `FrozenBlueprintPolicy` использует необрезанное распределение, то возникают две разные политики:

```
реальная continuation policy ≠ continuation policy в search
```

Из-за этого искажаются:

- belief updates по наблюдаемым действиям;
- reach weights;
- opponent likelihood;
- rollout continuation;
- root Q-values;
- итоговый MMDS update.

Нужно сделать **один канонический policy postprocessor**, используемый всеми путями:

```
network logits
→ legal-action mask
→ softmax
→ optional probability threshold
→ renormalization
→ deterministic fallback
```

И одинаково применять его в:

- реальном runtime inference;
- `FrozenBlueprintPolicy`;
- belief reconstruction;
- rollouts;
- evaluation.

Порог должен входить в checkpoint/runtime metadata, иначе одна и та же сеть может означать разные игровые политики.

## 2. Off-tree ставки и неравные стеки — блокеры реального применения

Fallback на нестандартной ставке — безопасное начальное поведение, но при реальной игре может оказаться слишком частым.

Нужно разделять:

### Восстановление игрового состояния

Движок должен уметь точно воспроизвести фактическую ставку, даже если такого размера нет в action abstraction.

### Оценка вероятности действия blueprint

Если blueprint такого действия не содержит, отдельно выбирается политика интерпретации:

- probabilistic mapping на соседние abstract sizings;
- interpolation между sizing buckets;
- nearest sizing как временный baseline;
- uncertainty penalty;
- fallback, если отображение ненадёжно.

То есть нельзя смешивать:

```
«состояние невозможно реконструировать»
```

и:

```
«blueprint не знает точной вероятности этого sizing»
```

Первое — недостаток игрового адаптера. Второе — нормальная проблема action abstraction.

Неравные стеки также нужно поддержать до реального использования. Но для текущего контролируемого HU `200/200` эксперимента это не мешает сначала доказать MMDS-гипотезу.

## 3. Нужен настоящий deadline

`max_depth` не заменяет ограничение wall-clock time.

Нужен контракт примерно такого вида:

```
decision_deadline_ms
safety_margin_ms
minimum_complete_particles
minimum_complete_rollouts
```

Поведение:

1. Проверить оставшееся время перед каждым новым batch.
2. Не начинать batch, который с высокой вероятностью не завершится.
3. Использовать только полностью завершённые paired samples.
4. При недостатке samples вернуть исходный blueprint.
5. Никогда не отдавать частично обновлённую или невалидную стратегию.

Полезно сделать anytime-режим:

```
8 particles
→ если осталось время, 16
→ 32
→ 64
```

Тогда качество растёт с доступным бюджетом, но решение всегда можно закончить безопасно.

## 4. Проверка только разницы двух лучших действий недостаточна

Текущий `best_gap_zscore` отвечает на узкий вопрос:

```
достаточно ли различаются две лучшие Q-оценки?
```

Но MMDS меняет **всё распределение**, а не только выбирает одно действие. Даже уверенный gap между двумя действиями не доказывает, что итоговая mixed policy лучше blueprint.

Нужна отдельная оценка candidate policy:

```
π_candidate = MMDS(π_blueprint, Q̂)
```

Затем на независимом validation batch оценить:

```
ΔEV = EV(π_candidate) − EV(π_blueprint)
```

Желательно с paired CRN:

- одинаковые private-state particles;
- одинаковые runouts;
- одинаковая continuation randomness;
- но samples должны быть независимы от тех, на которых строился update.

Иначе получится selection bias: одни и те же шумные samples сначала создают candidate, а затем «подтверждают» его преимущество.

Безопасный gate:

```
применить MMDS, только если
LCB(ΔEV) > minimum_required_gain
```

где `LCB` — нижняя граница доверительного интервала.

# Исправленный порядок работы

## Этап 1 — определить область доказательства

Пока только:

```
HU
equal stacks 200/200
postflop
фиксированный game contract
root-only MMDS
terminal blueprint rollouts
```

Не переносить результаты автоматически на 6-max.

## Этап 2 — унифицировать blueprint

- Общий legal mask.
- Общий threshold.
- Общая нормализация.
- Общий fallback.
- Тест на равенство распределений из `policy_runtime` и `FrozenBlueprintPolicy`.
- Сохранение semantics version в metadata.

Это сейчас приоритет №1.

## Этап 3 — закрыть корректность runtime

- `NaN/±inf`;
- минимальное число gap samples;
- deadline;
- атомарный fallback;
- детерминированность по seed;
- только полные paired samples;
- статистика latency p50/p95/p99.

## Этап 4 — независимая проверка update

Разделить samples:

```
search samples → построение MMDS candidate
validation samples → проверка candidate против blueprint
```

Проверять не только top-action gap, но и EV всей смешанной стратегии.

## Этап 5 — paired evaluation

Минимум три уровня:

1. `MMDS vs тот же frozen blueprint`.
2. `MMDS vs несколько прошлых checkpoints`.
3. `MMDS vs разные стили/эвристические opponents`.

Для каждого:

- смена позиций;
- одинаковые раздачи;
- независимые seed;
- confidence intervals;
- latency;
- fallback rate;
- изменение стратегии относительно blueprint.

## Этап 6 — off-tree coverage

После подтверждения работоспособности в контролируемых условиях:

- точная реконструкция нестандартных ставок;
- probabilistic action translation;
- unequal stacks;
- измерение доли ситуаций, уходящих в fallback.

## Этап 7 — только потом усложнение

Если root MMDS показывает устойчивый положительный эффект:

- sweep числа particles/runouts;
- sweep `eta`;
- один дополнительный future decision;
- сравнение depth 1 против depth 2 при одинаковом времени;
- boundary value network только при появлении truncated rollouts;
- ReBeL/CFR-subgame как отдельный конкурентный baseline, а не автоматическая замена.

# Итоговая оценка ответа Astra

Я согласен примерно со всем основным:

- **Да**, направление MMDS разумно.
- **Да**, моё слово «оптимальнее» было недоказанным.
- **Да**, текущая система — локальное root improvement, а не equilibrium subgame solver.
- **Да**, boundary value network прямо сейчас не обязательна.
- **Да**, единая семантика blueprint важнее добавления ещё одной статьи.
- **Да**, deadline, off-tree bets и unequal stacks являются реальными инженерными ограничениями.
- **Да**, преимущество нужно сначала показать экспериментально.
- **Да**, HU и 6-max необходимо рассматривать как разные этапы.

Единственное уточнение: отсутствие теоретической гарантии не делает MMDS плохим выбором. Оно означает, что статус должен быть таким:

> **MMDS остаётся текущим кандидатом для первой версии runtime search. Его не нужно переписывать, но пока нельзя считать доказанно сильным или безопасным solver. Следующий шаг — не новая архитектура, а исправление policy semantics и строгий экспериментальный proof.**
>
