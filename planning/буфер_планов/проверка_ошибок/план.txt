# ТЗ: надёжные проверки ошибок в обходе и обучении

## 1. Цель

Обеспечить следующее поведение:

- ошибочное действие или состояние не превращается в `return 0.0`;
- неудачная ветка не исключается молча из расчёта regrets;
- переключение strict mode действительно работает;
- повреждённые обходы не загрязняют replay-буферы;
- ошибка сопровождается достаточной диагностикой для воспроизведения.

**Не менять в рамках этой задачи:**

- ES/OS-схему;
- выбор оппонентов;
- формулы regret и discount;
- места сбора average-policy сэмплов;
- архитектуру сетей.

Перед изменениями проверить актуальный код и существующие регрессионные тесты.

## 2. Исправить чтение strict mode

В просмотренном коде использовалось:

```python
from src.utils.settings import STRICT_CHECKING
```

Такой импорт не видит последующее присваивание нового значения в исходном модуле.

Перейти на единый источник настройки, например:

```python
from src.utils import settings

if settings.is_strict_checking():
    ...
```

Требования:

- сохранить совместимый `set_strict_checking(...)`;
- проверка должна читать актуальное значение;
- найти аналогичные импорты во всём проекте;
- не создавать разные несогласованные strict-флаги для разных модулей.

Обязательный тест: переключение настройки **после импорта `deep_cfr`** меняет реальное поведение обхода.

## 3. Явно определить режимы обработки

Добавить в `config.yaml`:

```yaml
# Рекомендуемый режим для проверочных и новых обучающих запусков.
training_error_mode: strict

# Более дорогие проверки инвариантов движка.
training_validate_state_invariants: false

# Защита от продолжения обучения с массовыми сбоями.
training_max_failed_traversals_per_iteration: 3
```

Поддержать два режима:

### `strict`

Первая ошибка корректности:

1. записывает диагностику;
2. прекращает обход;
3. прерывает обучение исключением.

### `skip_traversal`

Ожидаемая ошибка игрового перехода или проверки состояния:

1. записывает диагностику;
2. отменяет **весь текущий корневой обход**;
3. не добавляет его данные в буферы;
4. позволяет перейти к следующему обходу.

При достижении лимита ошибок за итерацию — остановить обучение.

**Это новые предлагаемые настройки.** В документации явно указать изменение поведения: ошибки больше не маскируются нулевой ценностью.

## 4. Убрать молчаливые fallback в traversal

Проверить все места, где сейчас используются:

```python
except Exception:
    return 0.0
```

или пропуск действия через `continue`.

Для ошибки в любой ветке traverser нельзя:

- исключить эту ветку;
- перенормировать policy по оставшимся действиям;
- записать полученные regrets как корректный сэмпл.

Вместо этого ошибка должна дойти до границы корневого обхода.

Отдельно обработать:

- исключение при преобразовании действия;
- исключение при `apply_action`;
- `StateStatus`, отличный от `Ok`;
- отсутствие допустимых действий в нетерминальном состоянии;
- превышение защитной глубины;
- некорректные численные значения.

**Превышение глубины — не ничья и не нулевая награда.** Это диагностический сбой обхода.

Настоящий терминальный результат `0.0` остаётся допустимым.

## 5. Не сохранять частично испорченный обход

Ошибка может возникнуть после того, как другие ветки уже записали данные.

Поэтому в обоих режимах использовать временное накопление новых сэмплов на один корневой traversal:

```
начало traversal
    ↓
сбор во временные списки
    ↓
успешное завершение всех нужных веток
    ↓
commit в основные буферы
```

Если обход завершился ошибкой — временные сэмплы уничтожаются.

Относится ко всем буферам, которые заполняет данный обход:

- advantage;
- strategy;
- дополнительные обучающие буферы, если они уже существуют.

**Нельзя откатывать reservoir только уменьшением длины:** он мог заменить старые элементы. Безопаснее не изменять основной буфер до успешного завершения.

Не копировать целиком миллионные буферы ради этой защиты. Учесть память временного списка и измерить накладные расходы.

## 6. Добавить обязательные дешёвые проверки

### Политика и действия

- Размер policy и маски соответствует action space.
- Маска имеет допустимые значения.
- Вероятности конечны и неотрицательны.
- Нелегальные действия имеют нулевую вероятность с учётом установленного допуска.
- Сумма вероятностей близка к единице.
- Выбранное действие допустимо.
- Результат перехода имеет статус `Ok`.

Не «чинить» произвольную повреждённую policy скрытой перенормировкой. Допустимая нормализация должна оставаться частью обычного алгоритма, а не аварийным fallback.

### Обучающие данные

Перед commit:

- состояние, regrets и policy имеют ожидаемые формы;
- значения конечны;
- player ID и iteration корректны;
- нет некорректных масок.

### Обучение сети

- loss конечен;
- норма градиента конечна до шага оптимизатора.

При NaN/Inf **не выполнять шаг оптимизатора и остановить обучение**. Режим пропуска обхода не должен скрывать численную поломку обучения.

## 7. Дорогие проверки вынести отдельно

При `training_validate_state_invariants: true` проверять согласованные с движком инварианты:

- отсутствие повторяющихся карт;
- допустимые индексы игроков;
- конечность денежных величин;
- отсутствие недопустимых отрицательных стеков;
- сохранение фишек с учётом реальной семантики банка и ставок;
- корректность терминальных выплат.

**Сначала выяснить смысл полей `pot`, `bet_chips`, `pot_chips` в `pokers`.** Не добавлять проверку, которая дважды учитывает одни и те же деньги.

Для чисел с плавающей точкой использовать документированные допуски.

## 8. Разделить ошибки, которые можно и нельзя пропускать

Пропуск корневого обхода разрешить только для явно определённых ошибок игрового перехода/валидации.

Всегда останавливать процесс при:

- неожиданной программной ошибке;
- несовместимости моделей или checkpoint;
- CUDA OOM и нехватке памяти;
- неконечных loss/градиентах;
- повреждении структуры буфера.

Не перехватывать пользовательское прерывание и завершение процесса как «неудачную раздачу».

## 9. Диагностика и метрики

Для сбоя сохранять структурированную запись:

```
итерация
номер корневого traversal
traversing player
acting player
seed раздачи, если доступен
глубина
улица
слот и параметры действия
legal mask
использованная policy
статус движка
тип ошибки и traceback
последовательность действий до сбоя
версии кода и алгоритма, если доступны
```

Одного seed недостаточно для воспроизведения всех sampled-действий, поэтому сохранять путь действий либо соответствующее состояние RNG.

Полные игровые дампы могут содержать скрытые карты симулятора. Хранить их локально и не включать автоматически в общедоступные отчёты.

Метрики:

- attempted / successful / failed traversals;
- причины ошибок;
- число отменённых сэмплов;
- число достижений защитной глубины.

Оценочные раздачи с ошибками не учитывать как нулевую награду. По умолчанию прекращать оценку с диагностикой.

## 10. Тесты и критерии готовности

Обязательные регрессии:

1. Strict mode переключается после импорта модулей.
2. Ошибка `apply_action` действительно прерывает strict-обход.
3. Не-`Ok` статус не превращается в reward.
4. Сбой поздней ветки отменяет данные ранее пройденных веток.
5. Отмена не меняет заполненный reservoir и его счётчики.
6. В `skip_traversal` следующий исправный обход успешно сохраняется.
7. Лимит ошибок останавливает итерацию.
8. Depth limit не создаёт нулевую обучающую цель.
9. Настоящий terminal reward `0.0` принимается.
10. NaN/Inf останавливает обучение до шага оптимизатора.
11. На исправных контролируемых обходах ценности, regrets и policy targets сохраняют прежний смысл.
12. Проверен overhead на representative HU и six-max запуске.

**Итоговая гарантия этого изменения:** либо корневой обход завершился корректно и его данные приняты целиком, либо он явно завершился ошибкой и не внёс обучающих сэмплов. Ни одна техническая ошибка не должна незаметно становиться «покерным результатом».
