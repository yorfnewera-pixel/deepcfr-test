# ТЗ: переделать HU → six-max transfer без искусственной HU-проекции

## 1. Цель

Использовать обученного HU teacher для ускорения обучения six-max student, сохранив самостоятельное обучение student на six-max раздачах.

Устранить существующую неоднозначную проекцию:

```
six-max состояние
→ оставить hero и первого активного оппонента
→ сохранить общий банк
→ спросить HU teacher
```

**Не заменять её другим произвольным выбором оппонента.**

Статья Kdb использует перенос промежуточных признаков и выходов сетей. Однако это требует содержательно согласованных входов teacher/student; одна совместимость размеров тензоров недостаточна. [Kdb, разделы 3.1–3.2](https://github.com/yorfnewera-pixel/deepcfr-test/blob/c0df76cd8379f22da39a24f54fb13159e13313b5/Kdb-D2CFR-Solving-Multiplayer-imperfect-information-games-with-knowledge-distillation-based.md)

## 2. Разделить работу на два этапа

### Этап A — основной: перенос общих признаков при инициализации

Обучить HU teacher с выделенным общим карточным блоком. Передать этот блок в six-max student и продолжить обычное six-max обучение.

Это **warm-start через перенос весов**, не дистилляция выходов.

### Этап B — дополнительный: дистилляция на настоящих HU-состояниях

Если этап A работает, добавить вспомогательное обучение student на отдельных HU-примерах с ответами замороженного teacher.

**Не применять teacher-policy loss к настоящим six-max состояниям через урезание входа.**

Этапы должны включаться независимо. Не внедрять оба сразу без контрольных запусков.

## 3. Сначала проверить готовность HU teacher

Использовать согласованный HU-режим:

- отдельные advantage-сети P0/P1;
- обе стороны получают собственные regret-сэмплы;
- текущие regret-matching политики в обходах;
- перекрёстный сбор average-policy сэмплов;
- явно зафиксированный порядок snapshots и обновлений.

Для teacher выбирать checkpoint по независимой оценке, а не только по training loss или последнему номеру итерации.

Если общий policy teacher различает P0/P1, сохранять эту информацию в формате checkpoint. **Не усреднять две политики молча, чтобы убрать несовместимость интерфейса.**

## 4. Выделить переносимый блок архитектуры

Не пытаться копировать первые линейные слои существующей сети по совпадающим индексам: HU и six-max входы имеют разную структуру.

Предлагаемая архитектура:

```
карты hero + публичные карты + улица
                  ↓
             card_encoder
                  │
                  ├──────────────┐
                  ↓              ↓
       HU-контекстный блок    six-max-контекстный блок
                  ↓              ↓
             HU-выходы       six-max-выходы
```

Общий `card_encoder` должен получать одинаково определённые признаки:

- только собственные карты игрока;
- только уже открытые публичные карты;
- улицу;
- одинаковую канонизацию мастей и порядок признаков.

В него **не включать**:

- скрытые руки оппонентов;
- будущий борд;
- произвольно выбранного соперника;
- признаки мест, число которых различается между играми.

Контекстные блоки получают позиции, число игроков, стеки, ставки, банк и прочие игровые признаки.

**Карточное представление не становится универсальным автоматически:** обучение HU всё равно влияет на него. Поэтому после переноса student должен иметь возможность адаптировать его.

## 5. Этап A: перенос при старте student

При создании нового six-max запуска:

1. Загрузить и проверить teacher checkpoint.
2. Создать отдельную модель student.
3. Скопировать совместимый `card_encoder`.
4. Остальные six-max блоки инициализировать независимо.
5. Продолжить обучение на собственных six-max данных.

Для первой версии:

- переносить карточный блок policy-сети teacher в policy-сеть student;
- **не переносить напрямую финальные HU action/regret heads**;
- не переносить накопленные regrets, replay-буферы или оптимизаторы teacher;
- не связывать параметры teacher и student общими ссылками;
- не замораживать перенесённый блок student навсегда.

Если позднее переносится блок advantage-сети, это отдельный переключатель и эксперимент. Так будет видно, какой перенос полезен.

**Старый монолитный checkpoint нельзя автоматически считать совместимым с новой архитектурой.** При отсутствии выделенного блока — понятная ошибка или отдельно протестированная миграция, не загрузка с замалчиванием несовпадений.

## 6. Этап B: дополнительная HU-дистилляция

Этот этап нужен только после проверки warm-start.

Собирать отдельную обучающую выборку **настоящих HU-состояний**:

```
HU infoset
actor_id / роль
legal mask
полное распределение average policy teacher
версия teacher
```

Teacher работает без градиентов и не обновляется.

Для student добавить HU-входной адаптер и HU-policy head, использующие его общий карточный блок:

```
           общий блок student
           /                \
основной six-max путь    вспомогательный HU-путь
```

Обучение:

```
основной six-max loss
+ λ × KL(teacher_HU_policy || student_HU_policy)
```

Требования:

- teacher и вспомогательный HU-путь student получают одну и ту же реальную HU-ситуацию;
- маска действий совпадает;
- температура и её масштабирование в loss реализованы явно;
- коэффициент и вычислительный бюджет ограничены;
- предусмотрено затухание или отключение вспомогательного loss.

Это перенос знаний через общий блок, **а не заявление, что HU-policy является правильной целью для six-max решения**.

В первой реализации не добавлять value/regret-output distillation: её смысл и масштаб зависят от алгоритма накопления и требуют отдельного согласования.

## 7. Конфигурация

Предлагаемые новые параметры:

```yaml
teacher_transfer_enabled: false
teacher_transfer_checkpoint: null

# Первый реализуемый режим.
teacher_transfer_mode: card_encoder_warmstart

# Student адаптирует перенесённые признаки.
teacher_transfer_freeze_card_encoder: false

# Второй этап, по умолчанию отключён.
teacher_hu_aux_distillation_enabled: false
teacher_hu_aux_distillation_weight: 0.0
```

Режимы нельзя включать неявно через старый `teacher_strategy_checkpoint`.

Пока этап B не реализован, его включение должно выдавать понятную ошибку.

Старую six-max → HU output-проекцию убрать из рекомендуемого пути. При попытке использовать старую конфигурацию выводить явное предупреждение или ошибку миграции.

## 8. Checkpoint и продолжение обучения

Сохранять:

- версии архитектуры и encoding;
- источник перенесённых весов;
- режим переноса;
- какие блоки скопированы;
- параметры и состояние дополнительного HU-обучения, если оно включено.

**При resume не копировать teacher-веса поверх обученного student повторно.**

После этапа A teacher не нужен для обычного six-max обучения и инференса. После этапа B вспомогательный HU-путь не должен быть обязательным для игрового six-max инференса.

## 9. Проверки

Обязательные тесты:

- `transfer_enabled: false` сохраняет старое поведение.
- Карточные признаки одинаково кодируются в HU и six-max.
- Изменение скрытой руки оппонента не меняет policy-вход игрока.
- При старте копируются только разрешённые блоки.
- Учитель остаётся неизменным после шагов обучения student.
- Перенесённые student-параметры действительно могут обновляться.
- Resume не сбрасывает их обратно к teacher.
- В основном six-max пути не вызывается старая HU-проекция.
- При дополнительной дистилляции teacher/student видят одну HU-ситуацию и одну маску.

## 10. Как принять решение о пользе

Сравнить **одинаковую новую архитектуру student**:

- со случайной инициализацией;
- с HU warm-start.

Затем отдельно проверить добавление HU-дистилляции.

Это важно: сравнение новой архитектуры с переносом против старой архитектуры без переноса не выделяет эффект teacher.

Учитывать:

- качество six-max стратегии за одинаковое время;
- независимые seed и оценочные раздачи;
- стоимость предварительного обучения teacher;
- дополнительную стоимость вспомогательного loss.

---

**Мой выбор для первой поставки — этап A: перенос совместимого карточного блока, без подсказок teacher на искусственных HU-проекциях.** Это более узкая задача, чем полный Kdb, зато она проверяема и не заставляет six-max ученика имитировать ответы на другую игру. Если перенос помогает, следующим отдельным изменением добавляем этап B.
