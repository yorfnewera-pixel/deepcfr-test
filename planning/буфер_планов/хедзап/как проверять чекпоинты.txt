Да, такую утилиту сделать можно. Но сначала разделим понятия:

- **exploitability** — насколько checkpoint может эксплуатировать идеальный best response;
- **турнир checkpoint-ов** — практическая оценка того, становится ли новая версия сильнее старой.

Турнир **не вычисляет настоящую exploitability**, но для вашего большого HU это нормальный практический критерий.

## У вас уже есть основа

В репозитории уже существуют:

- `src/evaluation/paired_harness.py` — одинаковые раздачи и смена позиций;
- `tools/checkpoint_tools.py paired` — сравнение двух checkpoint с `bb/100`, standard error и 95% CI.

То есть с нуля писать evaluator не надо. Нужна обёртка вида `tools/hu_checkpoint_tournament.py`, которая автоматически выбирает checkpoint-ы и строит таблицу.

## Как правильно сравнивать checkpoint-ы

Сохранять checkpoint, например, каждые 10 000 итераций:

```
hu_checkpoint_iter_10000.pt
hu_checkpoint_iter_20000.pt
hu_checkpoint_iter_30000.pt
...
```

Но **10 000 — это период сохранения, а не критерий качества**.

На каждом этапе сравниваем:

```
новый checkpoint
против предыдущего checkpoint
против текущего champion
против фиксированного baseline 10k
```

Все матчи:

- на одинаковых раздачах;
- с одинаковыми seed;
- со сменой P0/P1;
- strategy network против strategy network;
- с замороженными весами;
- с результатом в `bb/100`;
- с 95% доверительным интервалом.

## Как выбирать победителя

Пример результата:

```
candidate: iter_50000
champion:  iter_40000

result: +3.2 bb/100
95% CI: [+1.1, +5.3]
```

Нижняя граница выше нуля — новый checkpoint статистически уверенно лучше:

```
iter_50000 становится champion
```

Если результат:

```
+1.2 bb/100
95% CI: [-2.0, +4.4]
```

это не победа и не доказательство равенства. Это означает: **данных недостаточно**. Нужно увеличить количество раздач.

Если:

```
-2.8 bb/100
95% CI: [-4.5, -1.1]
```

новый checkpoint уверенно хуже.

## Сколько раздач

Рекомендую двухступенчатую схему:

### Быстрый отбор

```
10 000 paired deals
× 3 независимых seed
× смена P0/P1
```

Это отбрасывает явно плохие checkpoint-ы.

### Финальное сравнение

Для близких кандидатов:

```
50 000–100 000 paired deals
× 3–5 seed
× смена P0/P1
```

В покере 100 или 1 000 раздач недостаточно: дисперсия слишком высокая.

## Критерий остановки обучения

Можно зафиксировать такой практический критерий:

> Остановить обучение, если пять последовательных checkpoint-ов, сохранённых через 10 000 итераций, не смогли статистически уверенно победить текущего champion, а ширина 95% CI в финальной оценке уже достаточно мала.
> 

То есть:

```
champion = 100k

110k не лучше
120k не лучше
130k не лучше
140k не лучше
150k не лучше

→ вероятное плато
→ остановить
→ оставить 100k как лучший checkpoint
```

Последний checkpoint необязательно лучший.

## Для сравнения обычного HU и D2CFR

Тут нельзя сравнивать только одинаковые номера итераций: D2CFR-итерация может стоить дороже.

Нужно сравнивать:

```
обычный HU после 24 часов
против
D2CFR после 24 часов
```

и дополнительно фиксировать:

- число traversals;
- wall-clock;
- количество собранных samples;
- seed;
- параметры сети.

## Что должна делать утилита

Предлагаемый интерфейс:

```bash
python tools/hu_checkpoint_tournament.py \
  --checkpoints models/hu_run \
  --step 10000 \
  --deals 10000 \
  --seeds 107 109 113 \
  --output reports/hu_tournament.json
```

Результат:

```
Iteration   Opponent   bb/100   CI95             Verdict
20k         10k        +4.2     [+1.3, +7.1]     promote
30k         20k        +0.8     [-1.7, +3.3]     inconclusive
40k         20k        +2.9     [+0.5, +5.3]     promote
50k         40k        -1.1     [-3.8, +1.6]     inconclusive

Champion: 40k
```

Также она должна проверять совместимость архитектуры, encoding и числа игроков и не смешивать несовместимые checkpoint-ы.

**Итог:** да, checkpoint имеет смысл сохранять каждые 10k, но сравнивать не «последние 10 тысяч», а каждый новый checkpoint с текущим чемпионом. Это будет ваш практический критерий прогресса, хотя формально это tournament strength, а не точная exploitability.
