**Да, основная схема согласована.** Осталось закрепить два решения, чтобы агент не трактовал их по-разному:

- обе advantage-сети замораживаются **на всю CFR-итерацию**, включая обе фазы;
- общая `strategy_net` должна различать P0/P1, поскольку их advantage-сети обучаются независимо.

Ниже — готовое ТЗ. **Оно касается только HU self-play и сбора средней стратегии. Не включает внедрение D2CFR, Q или дистилляции.**

# ТЗ: HU self-play с отдельными advantage-сетями и перекрёстным сбором average strategy

## 1. Цель и границы

Добавить отдельный HU-режим:

```
advantage_P0 → текущая политика P0 через regret matching
advantage_P1 → текущая политика P1 через regret matching

strategy_net → средняя стратегия по данным обеих сторон
```

Сохранить:

- существующий ES-обход;
- фиксированное пространство действий;
- текущую формулу накопления advantages, если она не изменена отдельной задачей;
- существующий six-max режим и его average/checkpoint-оппонентов.

**Не переносить изменения сбора strategy-сэмплов автоматически на six-max.**

Перед реализацией сверить актуальный код: предыдущий анализ мог предшествовать изменениям репозитория.

## 2. Включение режима

Добавить явный параметр:

```yaml
hu_current_policy_self_play: false
```

Для нового режима:

```yaml
hu_current_policy_self_play: true
num_players: 2
num_trainable_players: 2
```

Требования:

- по умолчанию старое поведение;
- при включённом режиме и несовместимых параметрах — понятная ошибка;
- checkpoint/average-оппоненты в новом HU traversal не используются;
- явно переданные настройки внешнего opponent pool отклоняются, а не игнорируются молча;
- при старте выводится выбранный режим и порядок обновлений.

Не использовать одно лишь `num_players: 2` для неявного переключения алгоритма.

## 3. Разделить обучаемое состояние игроков

Для каждого игрока нужны собственные:

- advantage-сеть;
- оптимизатор;
- advantage-буфер;
- target-сеть для bootstrap, если её использует выбранная формула обучения.

Дополнительно:

- одна общая `strategy_net` и её оптимизатор;
- один общий reservoir strategy-буфер;
- неизменяемые snapshots обеих текущих advantage-сетей для обходов.

**Не объединять роли сетей:**

- traversal snapshot определяет текущую политику;
- advantage target определяет bootstrap-цель.

Они могут содержать одинаковые веса на границе итерации, но имеют разное назначение.

Не копировать целиком существующий агент без необходимости. Выделить HU-координатор или небольшую отдельную ветку, переиспользуя encoder, action space, буферы и функции обучения.

## 4. Зафиксировать одну семантику итерации

Использовать общий замороженный профиль:

```
Начало итерации t:
    создать независимые snapshots advantage_P0 и advantage_P1
    подготовить advantage-буферы обоих игроков

Фаза P0:
    K ES-обходов за P0
    обе политики берутся из snapshots

Фаза P1:
    K ES-обходов за P1
    обе политики берутся из тех же snapshots

После обеих фаз:
    обучить advantage_P0 на данных P0
    обучить advantage_P1 на данных P1
    обновить соответствующие bootstrap targets
    обучить strategy_net по расписанию

Следующая итерация:
    создать новые snapshots
```

**Не обновлять политику P0 между фазами P0 и P1.** Последовательное обновление — другой допустимый вариант, но не часть этого ТЗ.

`K` означает число начальных обходов **на одного игрока**, не размер minibatch и не глубину дерева.

Snapshots должны быть настоящими копиями: сохранить `state_dict()` в переменную без клонирования тензоров недостаточно.

## 5. Изменить сбор данных только внутри нового HU-обхода

### В узлах traverser

- Кодировать состояние с позиции traverser.
- Получать policy из snapshot его advantage-сети через regret matching.
- Перебирать все допустимые действия.
- Вычислять ценность текущей стратегии и regrets.
- Записывать regret-сэмпл только в буфер этого игрока.
- **Не записывать strategy-сэмпл.**

### В узлах sampled opponent

- Кодировать состояние с позиции действующего игрока.
- Получать полное распределение из snapshot его advantage-сети.
- Применять legal mask и нормализацию.
- **До выбора действия** сохранять распределение в strategy-буфер.
- Сэмплировать действие из этого же распределения.

Итог:

```
Traverse P0:
    P0 → advantage_buffer_P0
    P1 → strategy_buffer

Traverse P1:
    P1 → advantage_buffer_P1
    P0 → strategy_buffer
```

Такой перекрёстный сбор соответствует структуре ES-псевдокода D2CFR.[[1]](https://arxiv.org/html/2105.12328v2)

## 6. Обеспечить совпадение target и sampling policy

В sampled-узле один раз вычислить:

```
policy = normalized_regret_matching(snapshot_output, legal_mask)
```

Это же распределение:

- записать как target;
- передать в выбор действия.

Запрещено:

- сохранять one-hot выбранного действия вместо распределения;
- сохранять average policy;
- сэмплировать из checkpoint policy;
- применять дополнительный probability floor только перед выбором действия;
- повторно вычислять target после обновления сети.

При отсутствии положительных regrets использовать единое, явно заданное правило fallback. Для первого варианта — равномерное распределение по допустимым действиям.

На невозможном действии или некорректной policy в проверочных запусках завершать работу с диагностикой, а не подставлять нулевую ценность.

## 7. Формат и обучение strategy-буфера

Сэмпл:

```
actor_id
encoded_infoset
policy[6]
legal_mask[6]
iteration
```

Требования:

- reservoir сохраняет историю между итерациями;
- обе фазы используют одинаковый номер итерации;
- бюджет обходов одинаков для обоих игроков;
- состояния кодируются для `actor_id`, не для traverser.

### Общая strategy-сеть должна различать игроков

Добавить HU-признак P0/P1 во вход strategy-сети либо эквивалентное условное представление.

Иначе независимые политики P0/P1 могут давать разные targets для одинакового относительного encoding, а общая сеть будет вынуждена их смешивать.

Это изменение версионировать. **Будущая интеграция с teacher–student проекцией должна учитывать новый формат, а не скрывать его.**

### Веса

Использовать явно заданное взвешивание по итерациям, согласованное с выбранным алгоритмом.

Не добавлять собственную reach probability «на всякий случай»: нужная зависимость от собственных действий уже участвует в частоте посещений sampled-стороны. Дополнительные поправки требуют отдельного вывода.

Новая схема исправляет механизм сбора, но не отменяет ошибок нейросетевой аппроксимации.

## 8. Checkpoint

Полный HU-checkpoint должен содержать:

- обе advantage-сети и их target-сети;
- оба advantage-оптимизатора;
- оба advantage-буфера, когда включено их сохранение;
- strategy-сеть, оптимизатор и reservoir;
- номер итерации;
- конфигурацию и версию encoding;
- состояния RNG для воспроизводимого продолжения;
- идентификатор HU-режима и порядка обновлений.

Сохранять на завершённой границе итерации. Для промежуточного сохранения потребовалось бы дополнительно восстанавливать фазу и её snapshots — это не включать в первую реализацию.

Старые checkpoint не преобразовывать молча в новый формат.

## 9. Обязательные тесты

### Маршрутизация сэмплов

На маленьком контролируемом дереве проверить:

- обход P0 пишет regrets только для P0, strategy — только для P1;
- обход P1 делает обратное;
- обе стороны попадают в общий strategy-буфер.

### Совпадение политики

Перехватить распределение, переданное в sampler, и сравнить с записанным target.

Включить случаи:

- несколько положительных regrets;
- отсутствие положительных regrets;
- нелегальные действия;
- единственное допустимое действие.

### Заморозка и обновление

- Обучение живой сети не меняет snapshot.
- Обе фазы одной итерации используют одинаковые версии.
- Каждый оптимизатор обновляет только своего игрока.
- Данные P0 не стираются при подготовке фазы P1.

### Усреднение

На небольшой игре проверить сбор относительно эталонного ES-накопителя при заранее заданных политиках. Проверять не только факт записи, но и ожидаемые частоты посещений и временные веса.

### Совместимость

- Сохранение и загрузка сохраняют предсказания.
- Старый six-max режим не меняет поведение.
- Общая strategy-сеть получает правильный `actor_id`.

## 10. Критерий завершения

Работа готова, когда:

- HU запускается отдельным флагом;
- в traversal нет вызовов average/checkpoint policy;
- regret-сэмплы принадлежат только traverser;
- strategy-сэмплы принадлежат только sampled opponent;
- target policy совпадает с sampling policy;
- обе advantage-сети действительно обучаются;
- новый режим проходит короткий HU smoke test;
- six-max остаётся нетронутым.

**Не включать в этот PR D2CFR-архитектуру, Q или дистилляцию. Сначала закрепить корректный HU-поток данных — затем остальные изменения можно добавлять независимо.**
