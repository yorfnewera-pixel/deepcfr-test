Да, в `planning/буфер_планов` сохранены все **активные инженерные направления**, которые мы сегодня согласовали:

- проверки ошибок;
- исправление aliasing через `history_summary_v3`;
- корректный HU self-play;
- опциональный D2CFR;
- HU teacher → six-max student.

Отдельного плана для Q нет — **это правильно**, его решили отложить. Six-max average/checkpoint pool тоже пока остаётся самостоятельным экспериментом и не должен автоматически меняться.

## Рекомендуемый порядок

### 1. Проверки ошибок

Сделать первым:

- рабочий strict mode;
- убрать `return 0.0` при технических ошибках;
- атомарный commit сэмплов целого traversal;
- NaN/Inf и диагностика;
- regression-тесты.

Это фундамент: иначе следующие изменения могут давать скрыто повреждённые данные.

### 2. `history_summary_v3`

Затем:

- public action history в Rust;
- новый encoder;
- перенос history через reconstruction/runtime;
- checkpoint format 6;
- снять `xfail`;
- smoke training и сравнение с v2.

Это нужно сделать до длительного обучения HU teacher, иначе teacher придётся переобучать после смены входа.

### 3. Корректный HU self-play

После стабилизации encoder:

- `advantage_P0` и `advantage_P1`;
- единые snapshots на обе фазы итерации;
- regrets только у traverser;
- strategy samples только у sampled opponent;
- actor-conditioned общая strategy-сеть;
- полный HU-checkpoint.

Six-max opponent pool при этом не менять.

### 4. Получить чистый HU baseline

До D2CFR и переноса teacher:

- провести короткие smoke runs;
- затем несколько полноценных HU запусков;
- проверить обе стороны, resume и стабильность;
- сохранить baseline по времени и качеству.

Без этого нельзя понять, помогли ли последующие изменения.

### 5. Опциональный D2CFR

Только поверх уже корректного HU-контура:

- отдельный флаг;
- отдельная dueling-модель и семантика целей;
- historical buffer;
- без Q, OS, Rainbow и MC-коррекции;
- сравнение с обычным HU за одинаковый wall-clock.

**D2CFR не делать обязательным:** выбрать его для итогового teacher только если эксперимент показывает пользу.

### 6. Подготовить архитектуру teacher transfer

До окончательного долгого обучения teacher:

- выделить общий `card_encoder`;
- разделить карточные и контекстные признаки;
- версионировать архитектуру;
- проверить, что HU и six-max одинаково кодируют общий карточный блок.

Это важно сделать заранее: старый монолитный teacher нельзя будет корректно использовать для запланированного warm-start.

### 7. Обучить окончательный HU teacher

Выбрать по измерениям:

- обычный HU либо D2CFR;
- только новая HU-схема;
- `history_summary_v3`;
- архитектура с выделенным `card_encoder`.

Checkpoint выбирать по независимой оценке, а не по training loss.

### 8. Teacher transfer — этап A

Сначала только:

- скопировать `card_encoder` teacher в six-max student;
- остальные блоки инициализировать независимо;
- student обучать на настоящих six-max данных;
- сравнить с той же архитектурой без warm-start.

Не использовать старую искусственную HU-проекцию.

### 9. Teacher transfer — этап B

Только если этап A дал пользу:

- дополнительная выборка настоящих HU-состояний;
- frozen teacher;
- вспомогательный HU-head student;
- небольшой отключаемый KL-loss;
- отдельная абляция стоимости и результата.

Value/regret distillation пока не добавлять.

## Короткая цепочка

```
Проверки ошибок
→ history_summary_v3
→ корректный HU self-play
→ HU baseline
→ опциональный D2CFR
→ модульный card_encoder
→ финальный HU teacher
→ six-max warm-start
→ при успехе вспомогательная HU-дистилляция
```

Единственная организационная рекомендация: **каждый пункт делать отдельным PR/коммит-серией с зелёными тестами и коротким benchmark до перехода дальше**. Не объединять encoder, HU sampling, D2CFR и teacher transfer в одну реализацию — тогда невозможно будет определить причину улучшения или поломки.
