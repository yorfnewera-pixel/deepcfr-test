# 1. Поддержать полный HU checkpoint в `FrozenBlueprintPolicy`

## Проблема

`FrozenBlueprintPolicy.from_checkpoint()` уже загружает:

```
strategy_only
hu_strategy_only
```

Но не может загрузить полный HU checkpoint:

```
checkpoint_kind = hu_current_policy_self_play
```

Полный HU checkpoint отличается от generic full checkpoint.

Generic схема:

```python
checkpoint["num_players"]
checkpoint["strategy_net"]
checkpoint["advantage_net"]
```

HU-схема:

```python
checkpoint["mode"]["num_players"]
checkpoint["mode"]["encoder_input_size"]
checkpoint["architecture"]["strategy"]
checkpoint["strategy"]["network"]
checkpoint["advantage_legs"]
```

Сейчас загрузчик требует корневой `num_players` до корректного определения формата и затем пытается разобрать HU-файл как generic full checkpoint.

## Требуемое поведение

`FrozenBlueprintPolicy.from_checkpoint()` должен поддерживать три отдельные схемы:

```
strategy_only
hu_strategy_only
hu_current_policy_self_play
```

Generic full checkpoint оставить отдельным существующим путём.

## 1.1. Сначала определить тип checkpoint

Не требовать корневой `num_players` до dispatch по `checkpoint_kind`.

Логика должна выглядеть примерно так:

```python
checkpoint_kind = checkpoint.get("checkpoint_kind")

if checkpoint_kind == "strategy_only":
    return load_generic_light_checkpoint(...)

if checkpoint_kind == "hu_strategy_only":
    return load_hu_light_checkpoint(...)

if checkpoint_kind == "hu_current_policy_self_play":
    return load_hu_full_checkpoint(...)

return load_generic_full_checkpoint(...)
```

## 1.2. Не дублировать строковые константы

Вынести публичные значения checkpoint kind в общий модуль, не создающий циклических импортов, например:

```python
GENERIC_STRATEGY_ONLY_KIND = "strategy_only"
HU_STRATEGY_ONLY_KIND = "hu_strategy_only"
HU_FULL_CHECKPOINT_KIND = "hu_current_policy_self_play"
```

Не импортировать приватную константу из `src/training/train.py` в evaluation, если это создаёт зависимость evaluation → training.

Подходящее место:

```
src/core/checkpointing.py
```

или отдельный модуль схем checkpoint.

## 1.3. Реализовать отдельный разбор полного HU checkpoint

Для полного HU checkpoint проверять:

```python
checkpoint["checkpoint_kind"] == "hu_current_policy_self_play"
checkpoint["checkpoint_format_version"]
checkpoint["hu_checkpoint_version"]
checkpoint["game_rules_version"]
checkpoint["action_space_version"]
checkpoint["action_labels"]
checkpoint["num_actions"] == 6
checkpoint["mode"]
checkpoint["architecture"]["strategy"]
checkpoint["strategy"]["network"]
```

Извлекать:

```python
num_players = checkpoint["mode"]["num_players"]
base_input_size = checkpoint["mode"]["encoder_input_size"]
encoding_version = checkpoint["mode"]["encoding_version"]
use_multi_agent = checkpoint["mode"]["use_multi_agent_advantage"]

strategy_schema = checkpoint["architecture"]["strategy"]
strategy_state = checkpoint["strategy"]["network"]
```

Для текущего HU-контракта проверить:

```
num_players == 2
strategy_input_size == base_input_size + 2
strategy actor count == 2
```

Полный HU checkpoint не обязан иметь `num_players` в корне.

## 1.4. Не загружать training state для evaluation

При загрузке полного HU checkpoint для frozen evaluation не нужно:

- создавать полноценный `DeepCFRAgent`;
- восстанавливать replay buffers;
- восстанавливать optimizers;
- восстанавливать RNG;
- загружать advantage-сети.

Нужно построить только strategy-сеть:

```python
strategy_net = PokerNetwork(
    strategy_input_size,
    hidden_size,
    NUM_ACTIONS,
    architecture,
)
strategy_net.load_state_dict(strategy_state, strict=True)
strategy_net.eval()
```

Это делает загрузку:

- быстрее;
- безопаснее;
- независимой от размера replay;
- пригодной для больших full checkpoints.

## 1.5. Сохранить actor conditioning

Полная HU strategy является общей сетью с двумя дополнительными признаками игрока.

При кодировании:

```python
base = encode_state_for_version(
    state,
    player_id,
    encoding_version,
)

actor = np.zeros(2, dtype=np.float32)
actor[player_id] = 1.0

strategy_input = np.concatenate([base, actor])
```

Не смешивать этот контракт с:

```
use_multi_agent_advantage
```

Это разные механизмы.

Для `probabilities_batch()` actor one-hot формировать по:

```python
state.current_player
```

Для `probabilities(state, player_id=...)` использовать явно переданный `player_id`.

## 1.6. Проверять фактические формы весов

До `load_state_dict` проверить, что declared architecture совпадает с tensors.

Для `card_context_v2` минимум:

```
card_encoder.0.weight
context_encoder.0.weight
fusion.0.weight
fusion.2.weight
action_head.weight
```

Проверить:

```
card input = 109
context input = strategy_input_size - 109
fusion input = hidden_size × 2
fusion output = hidden_size
action output = 6
```

Не доверять только metadata.

## 1.7. Проверять аргумент `num_players`

Сигнатуру можно оставить:

```python
from_checkpoint(
    path,
    *,
    num_players: int | None = None,
    device="cpu",
)
```

Поведение:

- если `num_players=None`, взять число игроков из соответствующей схемы checkpoint;
- если `num_players` передан явно, проверить совпадение;
- HU full checkpoint с `num_players != 2` отклонить.

## Тесты полного HU checkpoint

Добавить тесты:

1. Полный HU checkpoint загружается через:
    
    ```python
    FrozenBlueprintPolicy.from_checkpoint(full_path)
    ```
    
2. То же работает с:
    
    ```python
    num_players=2
    ```
    
3. `num_players=6` для HU checkpoint отклоняется.
4. Полный и соответствующий light checkpoint дают одинаковые logits.
5. Полный и light checkpoint дают одинаковые probabilities для P0.
6. Полный и light checkpoint дают одинаковые probabilities для P1.
7. Проверить batch, содержащий состояния с разными `current_player`.
8. Legal mask после загрузки работает одинаково.
9. Evaluation loader не восстанавливает replay buffers.
10. Evaluation loader не создаёт optimizers.
11. Повреждённая `architecture.strategy` отклоняется.
12. Несовместимый `strategy_input_size` отклоняется.
13. Отсутствующие два actor features отклоняются.
14. Generic full checkpoint продолжает загружаться старым путём.
15. `strategy_only` и `hu_strategy_only` не сломаны.

## Критерий готовности

Следующий сценарий должен работать:

```python
full_policy = FrozenBlueprintPolicy.from_checkpoint(
    "hu_checkpoint_iter_5000.pt"
)

light_policy = FrozenBlueprintPolicy.from_checkpoint(
    "hu_light_checkpoint_iter_5000.pt"
)

assert policies_match(full_policy, light_policy)
```

# 2. Закрыть `NaN/Inf` и малую выборку в runtime search

## Проблема

Сейчас решение приблизительно такое:

```python
if rollout_incomplete:
    fallback
elif best_gap_zscore < threshold:
    fallback
else:
    update_strategy
```

Для `NaN`:

```python
np.nan < threshold
```

возвращает `False`.

Поэтому неопределённая статистика может ошибочно попасть в ветку обновления strategy.

## Требуемый результат

Runtime search должен обновлять blueprint только при одновременно выполненных условиях:

1. Все необходимые rollouts успешно завершились.
2. Есть достаточное число paired samples.
3. `best_gap` определён и конечен.
4. `best_gap_se` определён либо корректно равен нулю.
5. `best_gap_zscore` определён.
6. Сигнал проходит установленный threshold.

В остальных случаях использовать blueprint fallback.

## 2.1. Возвращать число paired samples

Расширить `RolloutEvaluation`:

```python
best_gap_sample_count: int
```

Изменить `_root_signal_statistics()` так, чтобы он возвращал:

```python
(
    best_gap,
    best_gap_se,
    best_gap_zscore,
    best_gap_sample_count,
)
```

`best_gap_sample_count` должен равняться:

```python
differences.size
```

Если статистика не определена:

```
best_gap_sample_count = 0
```

## 2.2. Добавить минимальный размер выборки

В `RuntimeSearchConfig` добавить:

```python
min_root_gap_samples: int = 8
```

Валидация:

```python
if self.min_root_gap_samples < 2:
    raise ValueError(...)
```

Если для проекта нужен более мягкий контракт, допустимо начать с `4`, но значение должно быть явным и покрытым тестами.

Default `belief_particles=32` позволяет использовать порог `8` для второй половины paired evaluation.

## 2.3. Явно разделить случаи статистики

Рекомендуемый порядок:

```python
zscore = evaluation.best_gap_zscore
gap = evaluation.best_gap
gap_se = evaluation.best_gap_se
sample_count = evaluation.best_gap_sample_count

if np.any(evaluation.successful_rollouts != config.belief_particles):
    fallback("rollout_incomplete")

elif sample_count < config.min_root_gap_samples:
    fallback("rollout_insufficient_gap_samples")

elif not np.isfinite(gap):
    fallback("rollout_gap_undefined")

elif np.isnan(zscore):
    fallback("rollout_zscore_undefined")

elif np.isneginf(zscore):
    fallback("rollout_signal_below_noise")

elif np.isposinf(zscore):
    handle_positive_infinite_signal(...)

elif not np.isfinite(gap_se):
    fallback("rollout_gap_se_undefined")

elif zscore < config.min_root_gap_zscore:
    fallback("rollout_signal_below_noise")

else:
    update_strategy()
```

## 2.4. Явный контракт для `+inf`

`+inf` может появиться, если:

```
gap > 0
gap_se == 0
```

Это означает, что все paired differences в имеющейся выборке одинаковы.

Разрешать update при `+inf` только если:

```
sample_count >= min_root_gap_samples
gap конечен
gap > 0
gap_se == 0
все rollouts завершены
```

Добавить диагностический flag:

```
rollout_zero_variance_positive_signal
```

Если условия не выполнены — fallback.

Для:

```
gap == 0, gap_se == 0
```

использовать fallback.

Для `-inf` также fallback.

## 2.5. Проверить все значения до MMDS

Перед вызовом:

```python
mmds_update(...)
```

проверить:

```python
np.all(np.isfinite(evaluation.raw_ev_mean))
np.all(np.isfinite(mc_values[root_slots]))
np.all(np.isfinite(values_for_update))
```

Если нет — fallback, а не MMDS update.

Диагностический flag:

```
rollout_nonfinite_values_blueprint_fallback
```

## 2.6. Не маскировать причину fallback

В `SearchDecision.diagnostic_flags` должны различаться:

```
rollout_incomplete
rollout_insufficient_gap_samples
rollout_gap_undefined
rollout_gap_se_undefined
rollout_zscore_undefined
rollout_signal_below_noise
rollout_nonfinite_values
rollout_zero_variance_positive_signal
```

Это необходимо для последующей статистики runtime search.

## Тесты runtime search

Добавить детерминированные unit tests:

1. Один particle → fallback.
2. Два particles → fallback.
3. Недостаточно paired samples → fallback.
4. `best_gap_zscore=NaN` → fallback.
5. `best_gap=NaN` → fallback.
6. `best_gap_se=NaN` → fallback.
7. `best_gap_zscore=-inf` → fallback.
8. `gap=0`, `SE=0`, `zscore=0` → fallback.
9. `gap>0`, `SE=0`, `zscore=+inf`, но samples меньше порога → fallback.
10. `gap>0`, `SE=0`, `zscore=+inf`, samples достаточно → разрешён update с отдельным flag.
11. Конечный z-score ниже threshold → fallback.
12. Конечный z-score выше threshold → update.
13. Неполный rollout → fallback независимо от z-score.
14. `raw_ev_mean` содержит NaN → fallback.
15. `mc_values` не содержит NaN/Inf перед MMDS.
16. При fallback:
    
    ```python
    root_search_policy == root_blueprint_policy
    ```
    
17. При разрешённом update policy:
    - конечна;
    - неотрицательна;
    - нормирована;
    - не даёт массу illegal actions.

## Критерий готовности

Ни один неопределённый или недостаточно подтверждённый статистический сигнал не должен приводить к изменению blueprint strategy.

# 3. Зафиксировать контракт игры `SB=1 / BB=2 / stack=200`

Выбран **вариант A**: параметры игры не конфигурируются через YAML.

## Цель

У проекта должен быть один явный контракт обучающей игры:

```
Small blind: 1
Big blind: 2
Starting stack: 200
Формат: HU
Эффективная глубина: 100 BB
```

Пользователь не должен иметь возможность изменить неработающий параметр в YAML и ошибочно считать, что обучение изменилось.

## 3.1. Удалить фиктивную настройку

Удалить из `config.yaml`:

```yaml
big_blind: 2.0
```

Не добавлять:

```yaml
small_blind
starting_stack
```

Вариант A означает отсутствие изменяемых stakes в пользовательском конфиге.

## 3.2. Не оставлять необъяснимые magic numbers

Вместо непосредственных чисел внутри `_new_hand` добавить именованные константы:

```python
TRAINING_SMALL_BLIND = 1.0
TRAINING_BIG_BLIND = 2.0
TRAINING_STARTING_STACK = 200.0
TRAINING_STACK_DEPTH_BB = 100.0
```

Фабрика:

```python
def _new_hand(num_players: int, seed: int, button: int | None = None):
    ...
```

должна использовать только эти константы.

Если button пока вычисляется старым способом, не менять формулу button в этом задании.

## 3.3. Добавить структурированный игровой контракт

Желательно сформировать один объект:

```python
FIXED_TRAINING_GAME_CONTRACT = {
    "small_blind": 1.0,
    "big_blind": 2.0,
    "starting_stack": 200.0,
    "stack_depth_bb": 100.0,
}
```

Использовать его для:

- создания новой раздачи;
- run manifest;
- full HU checkpoint metadata;
- startup log;
- strict resume validation;
- документации.

Не дублировать значения по разным файлам.

## 3.4. Явно отклонять устаревшие настройки

Просто удалить `big_blind` из основного YAML недостаточно. Старый пользовательский конфиг может сохранить:

```yaml
big_blind: 5
```

а программа снова молча проигнорирует его.

При startup проверить наличие запрещённых legacy-ключей:

```
small_blind
big_blind
starting_stack
stake
stack_size
```

Если они присутствуют в пользовательском config, завершить запуск с понятной ошибкой:

```
Training stakes are fixed at SB=1, BB=2, stack=200.
Remove big_blind from config; configurable stakes are not supported.
```

Агент должен сначала изучить текущий config loader и реализовать проверку через его штатный интерфейс, не читать YAML вторым независимым способом.

Если некоторые перечисленные ключи используются в другом подтверждённом контексте, отклонять только те, которые претендуют на управление обучающей раздачей.

## 3.5. Записать контракт в checkpoint

В full HU checkpoint добавить:

```python
"game_contract": {
    "small_blind": 1.0,
    "big_blind": 2.0,
    "starting_stack": 200.0,
    "stack_depth_bb": 100.0,
}
```

Добавить тот же объект в:

```
run_manifest.json
HU light checkpoint
```

При resume сравнивать его с текущим fixed contract.

При evaluation также проверять контракт, чтобы модель, обученная под другой масштаб игры, не загружалась молча.

Поскольку фактические правила и значения не меняются, не повышать:

```
GAME_RULES_VERSION
```

только из-за добавления metadata.

Но если новое поле становится обязательным для HU checkpoint, повысить:

```
HU_CHECKPOINT_VERSION
```

например, с `3` до `4`, либо реализовать явно документированную миграцию. Не делать неявный fallback для неизвестного игрового контракта.

## 3.6. Startup log

При старте HU обучения печатать:

```
Game contract: Heads-Up NLHE, SB=1, BB=2, starting stack=200 (100 BB).
Stakes are fixed and cannot be changed through config.
```

Это должно быть видно до первой итерации.

## 3.7. Обновить документацию

В README указать:

- обучение поддерживает фиксированный HU `1/2`;
- начальный стек `200`;
- глубина `100 BB`;
- YAML не управляет stakes;
- для другого размера блайндов требуется отдельное изменение игрового контракта;
- старые checkpoints без metadata нового контракта могут быть несовместимы;
- `advantage_reward_scale: 200` не является настройкой стартового стека — это масштабирование targets.

Последний пункт особенно важен, чтобы не путать:

```yaml
advantage_reward_scale: 200
```

со stack size.

## Тесты фиксированного контракта

Добавить тесты:

1. `_new_hand()` создаёт:
    
    ```
    sb == 1
    bb == 2
    initial stack == 200
    ```
    
2. Глубина равна `100 BB`.
3. В `config.yaml` отсутствует `big_blind`.
4. Legacy `big_blind` в config вызывает явную ошибку.
5. Legacy `small_blind` вызывает ошибку.
6. Legacy `starting_stack` вызывает ошибку.
7. Full checkpoint содержит `game_contract`.
8. Light checkpoint содержит тот же `game_contract`.

## Критерий готовности

После изменения не должно существовать ситуации:

```

→ программа продолжила обучение на BB=2 без предупреждения
```

Либо параметра нет, либо устаревший параметр вызывает fail-fast.
