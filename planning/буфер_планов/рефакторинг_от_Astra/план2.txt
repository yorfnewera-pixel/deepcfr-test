# 1. Исправить ограничение `card_context_v1`

## Проблема

В текущей архитектуре:

```python
card_embedding = card_encoder(cards)
context_embedding = context_encoder(context)
embedding = torch.cat([card_embedding, context_embedding])
output = linear_head(embedding)
```

После объединения признаков сразу стоит линейная голова. Поэтому выход имеет аддитивную форму:

```
output(cards, context) = f(cards) + g(context)
```

Сеть не может полноценно моделировать нелинейные взаимодействия между:

- картами;
- размером банка;
- эффективным стеком;
- позицией;
- легальными действиями;
- историей ставок.

## Требуемое решение

### 1.1. Не менять семантику существующей архитектуры

Не модифицировать `card_context_v1` на месте.

Добавить новую архитектуру:

```python
CARD_CONTEXT_V2_ARCHITECTURE = "card_context_v2"
```

Причина: старые checkpoints с названием `card_context_v1` должны продолжать однозначно описывать старую структуру.

### 1.2. Добавить общий nonlinear fusion trunk

Для `PokerNetwork` и `DuelingRegretNetwork`:

```python
card_embedding = card_encoder(card_features)
context_embedding = context_encoder(context_features)
combined = torch.cat([card_embedding, context_embedding], dim=-1)
joint_embedding = fusion(combined)
```

Базовый вариант:

```python
self.fusion = nn.Sequential(
    nn.Linear(hidden_size * 2, hidden_size),
    nn.ReLU(),
    nn.Linear(hidden_size, hidden_size),
    nn.ReLU(),
)
```

После этого головы должны получать `joint_embedding`.

Для strategy-сети:

```python
logits = action_head(joint_embedding)
```

Для D2CFR:

```python
V = state_value_head(joint_embedding)
Q = action_value_head(joint_embedding)
R = Q - V
```

Не изменять контракт:

```
regrets == action_values - state_values
```

### 1.3. Сохранить отдельный `card_encoder`

Методы должны продолжить работать:

```python
encode_cards(...)
encode_context(...)
```

Это необходимо для HU → 6-max teacher transfer.

При переносе из HU:

- копировать только `card_encoder`;
- `context_encoder`, `fusion` и головы инициализировать согласно целевой сети;
- проверять архитектуру и размер card-признаков;
- не пытаться копировать fusion между несовместимыми HU/6-max сетями.

### 1.4. Обновить конфиг

После реализации переключить активный режим:

```yaml
network_architecture: card_context_v2
```

`card_context_v1` оставить поддерживаемым для явной загрузки старых моделей.

### 1.5. Обновить checkpoint metadata

Описание архитектуры должно включать минимум:

```python
{
    "network_architecture": "card_context_v2",
    "card_feature_size": 109,
    "input_size": ...,
    "hidden_size": ...,
    "fusion_input_size": hidden_size * 2,
    "fusion_output_size": hidden_size,
    "num_actions": 6,
}
```

При resume:

- checkpoint `card_context_v1` не должен загружаться в `card_context_v2`;
- checkpoint `card_context_v2` не должен загружаться в `card_context_v1`;
- ошибка должна быть явной до `load_state_dict`;
- архитектурное изменение не следует маскировать повышением `GAME_RULES_VERSION`, поскольку правила игры здесь не меняются.

### 1.6. Инициализация

Сохранить корректный нулевой старт выходных голов, если он является частью текущего контракта:

```python
action_head.weight = 0
action_head.bias = 0
state_value_head.weight = 0
state_value_head.bias = 0
```

Случайно инициализированный fusion при нулевых головах не должен создавать ненулевые начальные regrets или logits.

## Тесты архитектуры

Добавить тесты:

1. `card_context_v1` по-прежнему создаётся и имеет старую структуру.
2. `card_context_v2` содержит fusion trunk.
3. `PokerNetwork(card_context_v2)` выдаёт форму:
    
    ```
    [batch, 6]
    ```
    
4. `DuelingRegretNetwork(card_context_v2)` выдаёт:
    - `V: [batch, 1]`;
    - `Q: [batch, 6]`;
    - `R: [batch, 6]`.
5. Численно выполняется:
    
    ```python
    regrets == action_values - state_values
    ```
    
6. Сеть допускает interaction между card/context, а не только сумму независимых эффектов.
7. Старый `card_context_v1` checkpoint отвергается при загрузке в v2.
8. Полный HU checkpoint v2 проходит save/load round-trip.
9. Light checkpoint v2 загружается runtime-инференсом.
10. Teacher transfer корректно переносит `card_encoder` из совместимого HU checkpoint.

# 2. Исправить `from_mid_hand(stage=Showdown)`

## Проблема

Сейчас можно создать состояние:

```
stage = Showdown
final_state = false
legal_actions = []
rewards = 0
```

Такое состояние нельзя корректно продолжить или завершить.

## Предварительная проверка

До изменения API найти все вызовы:

```
from_mid_hand(
```

Проверить отдельно:

- runtime search;
- rollouts;
- evaluation;
- tests;
- восстановление скрытых карт;
- Python-обёртки.

Определить, требуется ли проекту восстановление уже наступившего Showdown.

## Предпочтительное решение для текущего этапа

Если завершённый Showdown нигде не требуется, запретить его:

```rust
if stage == Stage::Showdown {
    return Err(InitStateError {
        msg: "from_mid_hand cannot restore an unresolved Showdown state".to_owned(),
    });
}
```

Это безопаснее, чем частично реализовать settlement без полного контракта side pots.

## Альтернативное решение

Реализовывать автоматическое завершение Showdown только если проект действительно использует такой вход.

В таком случае конструктор должен сразу:

1. Рассчитать ранги всех активных игроков.
2. Определить победителей.
3. Корректно распределить выплаты.
4. Выставить:
    
    ```
    final_state = true
    legal_actions = []
    ```
    
5. Заполнить rewards.
6. Проверить zero-sum.

Не делать упрощённое автоматическое завершение, если оно неправильно работает с:

- несколькими all-in;
- различными вложениями;
- side pots;
- ничьими.

Если полноценный settlement не реализуется сейчас — Showdown нужно отклонять.

## Тесты Showdown

Добавить тесты:

1. `from_mid_hand(stage=Showdown)` выдаёт ожидаемую ошибку, если выбран запрет.
2. Нельзя получить состояние одновременно:
    
    ```
    final_state == false
    legal_actions.is_empty()
    ```
    
3. Обычные `Preflop/Flop/Turn/River` состояния продолжают восстанавливаться.
4. Ошибка конструктора понятная и детерминированная.
5. Runtime search не передаёт `Showdown` в `from_mid_hand`.

# 3. Убрать угадывание `current_player` в `from_mid_hand`

## Проблема

При:

```python
current_player=None
```

конструктор выбирает первого активного игрока после button.

Для HU preflop это может назначить BB, хотя в начале preflop первым действует button/SB.

Но просто заменить правило на «button действует первым preflop» недостаточно: `from_mid_hand` может восстанавливать не начало улицы, а произвольную середину торговли.

## Требуемое решение

Сделать `current_player` обязательным по смыслу для `from_mid_hand`.

Предпочтительный безопасный вариант:

- временно сохранить тип `Option<u64>` для совместимости Python API;
- при `None` возвращать явную ошибку;
- обновить все внутренние call sites, чтобы они всегда передавали actor.

Например:

```rust
let current_player = match current_player {
    Some(player)
        if player < n_players
        && players_state[player as usize].active =>
    {
        player
    }
    Some(_) => {
        return Err(InitStateError {
            msg: "current_player must identify an active player".to_owned(),
        });
    }
    None => {
        return Err(InitStateError {
            msg: "current_player is required for from_mid_hand".to_owned(),
        });
    }
};
```

После обновления всех потребителей можно сделать аргумент обязательным и на уровне Python-сигнатуры.

## Что нельзя делать

Не определять actor только по:

- button;
- stage;
- списку active players;
- размеру ставок.

Для произвольной середины улицы этой информации недостаточно.

## Тесты actor contract

Добавить тесты:

1. `current_player=None` отклоняется.
2. Активный корректный player принимается.
3. Неактивный player отклоняется.
4. Player за пределами диапазона отклоняется.
5. HU preflop можно явно восстановить с button/SB как actor.
6. HU preflop после raise можно явно восстановить с BB как actor.
7. HU postflop можно явно восстановить с BB как первым actor.
8. Six-max восстановление не изменяет идентификаторы игроков.
9. Все runtime-search вызовы передают actor явно.

# 4. Добавить очистку HU full checkpoints

## Проблема

Generic checkpoints проходят pruning, а HU checkpoints сохраняются через отдельный путь:

```python
_save_hu_checkpoint(...)
```

и накапливаются без удаления.

Полный HU checkpoint содержит replay-буферы и optimizer state, поэтому длинное обучение может заполнить диск.

## Требуемое решение

### 4.1. Не использовать generic retention без адаптации

Generic checkpoint pool может требовать много прошлых моделей для multiway opponent pool. HU resume не требует хранения такого же количества огромных full checkpoints.

Добавить отдельную HU retention policy.

Предлагаемые параметры:

```yaml
hu_checkpoint_keep_recent: 2
hu_checkpoint_keep_milestones: 2
```

Существующий параметр:

```yaml
checkpoint_keep_every: 50000
```

использовать как период milestone.

При:

```yaml
hu_checkpoint_save_every: 5000
checkpoint_keep_every: 50000
hu_checkpoint_keep_recent: 2
hu_checkpoint_keep_milestones: 2
```

хранить:

- два последних обычных HU full checkpoint;
- два последних milestone, кратных `50000`;
- `hu_checkpoint_final.pt`;
- соответствующие light checkpoints.

### 4.2. Обобщить поиск checkpoints по префиксу

Например:

```python
def _prune_full_checkpoints(
    directory,
    *,
    prefix,
    historical_every,
    keep_recent,
    keep_historical,
):
    checkpoints = _checkpoint_paths(directory, prefix)
    ...
```

Для generic:

```python
prefix = _HEAVY_CHECKPOINT_PREFIX
```

Для HU:

```python
prefix = _HU_HEAVY_CHECKPOINT_PREFIX
```

Не смешивать:

```
multi_checkpoint_iter_*.pt
hu_checkpoint_iter_*.pt
light_checkpoint_iter_*.pt
```

### 4.3. Порядок сохранения

На checkpoint-итерации:

1. Атомарно сохранить HU full checkpoint.
2. Выполнить pruning HU full checkpoints.
3. Сохранить соответствующий light checkpoint.
4. Удалить light checkpoints, у которых больше нет соответствующего HU full checkpoint.
5. Не затрагивать final checkpoint.

Если full checkpoint не сохранился, нельзя удалять предыдущий resumable checkpoint.

### 4.4. Логирование

После pruning выводить кратко:

```
HU checkpoint retention:
kept recent: [...]
kept milestones: [...]
deleted: [...]
```

Не печатать содержимое checkpoint или внутренние tensors.

## Тесты checkpoint retention

Добавить тесты во временной директории:

1. Создать HU checkpoints:
    
    ```
    5000, 10000, 15000, 50000, 55000, 100000, 105000
    ```
    
2. Проверить, что остаются:
    - нужное количество последних;
    - нужное количество milestone.
3. Generic checkpoints не удаляются HU-pruning.
4. HU checkpoints не удаляются generic-pruning.
5. `hu_checkpoint_final.pt` не удаляется.
6. Light checkpoint без соответствующего full удаляется.
7. Light checkpoint с сохранённым full остаётся.
8. Последний resumable full checkpoint всегда сохраняется.
9. Повторный pruning идемпотентен.
10. Неизвестные имена файлов не удаляются.
