Твоё ощущение **частично правильное**: последние планы и ревью действительно были сильно сфокусированы на HU, потому что:

1. В текущем конфиге стоит `num_players: 2`.
2. Активен отдельный `hu_current_policy_self_play`.
3. Текущий D2CFR прямо ограничен первым этапом — HU.
4. Большая часть недавно добавленного кода — новый HU coordinator, две advantage-ноги, actor-conditioned strategy и отдельные HU checkpoints.
5. Astra проверяла прежде всего активный путь исполнения, а не будущий 6-max.

Поэтому большое количество HU-ошибок связано одновременно и с **новизной режима**, и с **ограниченной областью проверки**.

# Важный момент: сейчас нельзя просто поставить `num_players: 6`

В актуальном коде есть явная защита приблизительно такого смысла:

```python
if d2cfr_enabled:
    if num_players != 2:
        raise ValueError("D2CFR этапа 1 поддерживает только HU")
    if not hu_current_policy_self_play:
        raise ValueError("D2CFR этапа 1 требует HU coordinator")
```

Поэтому переключение:

```yaml
num_players: 6
d2cfr_enabled: true
```

сейчас должно завершиться ошибкой.

Это хорошо: система не притворяется, что HU-D2CFR автоматически является корректным 6-max D2CFR.

Переход предполагается примерно такой:

```
Этап A:
новый HU D2CFR run
→ обучаем card_encoder
→ сохраняем полный HU checkpoint

Этап B:
новый 6-max run
→ создаём новые 6-max сети и buffers
→ переносим только card_encoder из HU
→ остальное обучаем заново
```

То есть это **не resume HU checkpoint с заменой 2 на 6**.

# Какие исправления были только для HU

Эти вещи почти полностью HU-специфичны:

- button одновременно является SB;
- button/SB действует первым preflop;
- BB действует первым postflop;
- две независимые advantage-сети P0/P1;
- HU coordinator с порядком:
    
    ```
    traverse P0
    traverse P1
    train P0
    train P1
    train shared strategy
    ```
    
- два дополнительных actor-признака P0/P1 в strategy;
- `hu_strategy_only`;
- полный HU checkpoint с двумя advantage-ногами;
- HU checkpoint retention;
- HU run manifest;
- баланс Button/BB при одном traversal.

При переходе на 6-max эти механизмы нельзя механически расширить.

Например, двухмерный actor one-hot:

```
[P0, P1]
```

не является готовым решением для шести игроков.

# Какие исправления полезны и для 6-max

Значительная часть проделанной работы является общей фундаментальной базой.

## Исправления движка

Применяются ко всем форматам:

- правильное различие check и call;
- размер `call_amount`;
- минимальный шаг рейза;
- short all-in;
- обязательный `last_raise_increment`;
- корректный wheel `A-2-3-4-5`;
- явный `current_player` при реконструкции;
- запрет незавершённого Showdown;
- проверка legal actions.

## Архитектура

`card_context_v2` полезна для любого числа игроков:

```
card_encoder
context_encoder
nonlinear fusion
heads
```

Она устраняет аддитивное ограничение карт и контекста как в HU, так и в 6-max.

При переносе HU → 6-max сохраняется только:

```
card_encoder
```

Это разумно, потому что:

- карточные паттерны частично переносимы;
- контекст шестиместного стола другой;
- размеры positional features другие;
- ranges и betting dynamics другие;
- fusion и heads должны адаптироваться к 6-max.

## Replay и checkpoints

Общими являются:

- разделение `_size` и `_total_seen`;
- reservoir sampling;
- запрет чтения неинициализированных строк;
- strict capacity resume;
- version metadata;
- atomic save;
- проверка tensor shapes;
- изоляция запусков.

Хотя конкретные схемы HU и 6-max checkpoints разные, принципы одинаковы.

# Чего действительно будет не хватать для 6-max

Перед шестью игроками нужен отдельный аудит. HU-исправления не закрывают следующие области.

## 1. Полноценный multiway training coordinator

Нужно проверить контракт для всех traversers:

```
P0, P1, P2, P3, P4, P5
```

На одну CFR-итерацию должно быть понятно:

- какие сети заморожены;
- когда собираются данные каждого игрока;
- когда начинается обучение;
- очищается ли что-либо между traversers;
- кто записывает strategy samples;
- какая policy используется оппонентами.

Корректный общий принцип:

```
заморозить профиль всей итерации
→ собрать traversal для всех нужных traversers
→ не потерять samples предыдущих traversers
→ только потом обучать сети
```

Ранее именно в generic multiplayer пути уже находилась ошибка очистки буфера между traversers. Даже если её исправили, весь путь нужно проверить целиком тестами.

## 2. Семантика advantage-сетей

Нужно заранее выбрать архитектуру:

### Вариант 1: одна общая advantage-сеть

Сеть получает достаточную информацию о позиции/игроке и обучается на samples всех traversers.

### Вариант 2: шесть независимых advantage-сетей

По одной на каждое фиксированное место.

Это намного дороже по:

- памяти;
- optimizer steps;
- checkpoints;
- replay;
- времени обучения.

### Вариант 3: общая сеть с player/position conditioning

Обычно практичнее, но необходимо строго решить, что означает conditioning:

- абсолютный player ID;
- позиция относительно button;
- позиция относительно hero;
- UTG/HJ/CO/BTN/SB/BB;
- число активных игроков.

Текущий HU one-hot P0/P1 сам по себе этого не решает.

## 3. Позиции и ротация button

Для 6-max нужно проверить, что каждый traverser равномерно видит:

```
BTN
SB
BB
UTG
HJ
CO
```

Недостаточно просто чередовать `button % 2`.

Нужен тест распределения:

```
каждый trainable player × каждая относительная позиция
```

При малом числе traversals позиционный баланс должен сохраняться между итерациями.

## 4. Side pots

Это, вероятно, главный блокер движка для настоящего 6-max.

Текущий `set_winners` не реализует полноценные:

- main pot;
- side pot;
- несколько side pots;
- разные all-in levels;
- folded contributions;
- ничью в main pot;
- разных победителей main и side pots;
- odd chips.

В HU с равными стартовыми стеками это обычно не мешает. В 6-max all-in с разными остаточными стеками — обычный сценарий.

До исправления side pots 6-max traversal может выдавать неправильные terminal utilities, а значит сеть будет обучаться на математически неправильных targets.

## 5. Размер representation

При переходе от двух к шести игрокам меняются:

- `button` features;
- `current_player` features;
- player state blocks;
- history summary;
- raise actor features;
- размер context encoder;
- полный input size.

Поэтому HU full network нельзя загрузить в 6-max. Именно поэтому план предусматривает перенос только `card_encoder`.

Нужно отдельно протестировать:

```
encode_state для всех шести player_id
```

и инвариантность относительно циклической перенумерации мест.

## 6. Масштаб replay и обучение

6-max имеет гораздо больше:

- decision nodes;
- infosets;
- позиций;
- betting histories;
- opponent configurations.

Буферы:

```yaml
advantage_memory_size: 100000
strategy_memory_size: 200000
```

которые могут быть приемлемы для HU, не обязаны быть достаточными для 6-max.

Также нельзя автоматически переносить:

```
75 advantage steps
500 strategy steps
```

В six-max покрытие данных на одну сеть будет другим.

Понадобятся метрики:

- buffer fill;
- eviction rate;
- equivalent epochs;
- samples по traverser;
- samples по позиции;
- samples по улице;
- held-out loss;
- время обхода;
- время обучения.

## 7. Оценка качества

Для HU достаточно сравнивать две позиции с seat swap.

Для 6-max нужна ротация по всем местам:

```
агент играет каждую из шести позиций
оппоненты переставляются
одинаковые seeds/decks используются для сравниваемых вариантов
```

Оценка только против random будет особенно слабой.

Нужен frozen checkpoint pool и отчёт отдельно по:

- BTN;
- blinds;
- early position;
- общей средней;
- дисперсии;
- доверительному интервалу.

## 8. Теоретическая граница

D2CFR и классические гарантии CFR в первую очередь ориентированы на двухсторонние zero-sum игры.

6-max poker сохраняет нулевую сумму денег за столом, но это уже **многосторонняя игра**. Стандартная гарантия сходимости CFR к Nash equilibrium для двух игроков zero-sum не переносится автоматически в том же виде.

Это не означает, что обучать 6-max таким методом нельзя. Но результат следует называть:

```
практическая multiplayer self-play стратегия
```

а не доказанно сходящимся решателем полного 6-max NLHE.

# Почему сейчас всё равно полезно довести HU

Это не пустая работа. HU позволяет проверить в более контролируемой форме:

- корректность движка;
- D2CFR targets;
- две стороны self-play;
- historical replay;
- reinitialize contract;
- Dueling `Q/V/R`;
- архитектуру card encoder;
- checkpoints и resume;
- влияние train steps;
- реальное улучшение против frozen policies.

Если эти основы не работают в HU, в 6-max разобраться будет ещё сложнее.

Проблема возникнет только если считать:

> «Раз HU заработал, значит достаточно поставить `num_players: 6`».
> 

Вот это неверно.

# Как правильно организовать переход

Я бы разделил проект на явные этапы.

## Stage A — HU D2CFR

Закрыть:

- корректность двух позиций;
- engine tests;
- full/light checkpoints;
- stable training;
- MSE/Huber A/B;
- train-step A/B;
- frozen evaluation;
- переносимый `card_encoder`.

## Stage B — 6-max readiness audit

До написания кода отдельно проверить:

- multiway terminal settlement и side pots;
- generic traversal;
- buffer lifecycle;
- strategy sampling;
- frozen profile;
- positional coverage;
- encoder;
- checkpoint schemas;
- evaluation;
- ресурсы.

## Stage C — новый 6-max run

Создать:

- новые сети;
- новые replay buffers;
- новый run manifest;
- новый checkpoint namespace;
- новый config;
- новый positional contract.

Из HU checkpoint перенести только разрешённую часть:

```
card_encoder
```

## Stage D — 6-max validation

До длинного запуска:

- engine all-in/side-pot tests;
- 6-position coverage test;
- smoke traversal каждого игрока;
- buffer accounting;
- save/resume;
- seat-rotated evaluation;
- небольшой controlled run.

# Итог

Да, последние планы были **намеренно HU-центричными**, потому что сейчас активен и реализован именно HU D2CFR Stage A. Многие ошибки возникли из-за новизны отдельного HU пути.

Но это не означает, что после их исправления 6-max готов. Наоборот, код сейчас специально блокирует прямое включение D2CFR при шести игроках.

Правильная стратегия:

```
довести HU
→ провести отдельный 6-max readiness audit
→ реализовать недостающий multiplayer контракт
→ начать новый 6-max run
→ перенести только card_encoder
```

Самые крупные будущие блокеры 6-max — это **side pots, корректный multiway coordinator, позиционное покрытие шести мест и отдельная проверка multiplayer training semantics**.
