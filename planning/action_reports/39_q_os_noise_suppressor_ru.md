================================================================================
ОПИСАНИЕ
================================================================================

При Outcome Sampling на postflop multiway regrets для unsampled действий
полностью определяются Q-baseline:

  regret[a] = Q(s,a) - EV_hat   (для unsampled actions)

Качество OS-regrets = качество Q-сети. Плохой Q → шумные regrets →
шумный advantage signal → хуже advantage_net → хуже strategy/sampling.

Q-сеть — усреднитель шума. Каждый переход (state, action → reward) — одно
наблюдение. Обучение на этих наблюдениях — калибровка предсказаний.
Больше примеров → точнее среднее → тише шум.

Петля самоусиления:
  OS → больше данных в q_buffer → Q учится точнее → OS-regrets меньше шума
  ↑                                                         ↓
  └───────── advantage network лучше сходится ──────────────┘

Проблема: train_q_network делает 2 optimizer steps за итерацию (epochs=2),
независимо от того, включён OS или нет. При OS Q-сеть критичнее,
но обучается столько же.

================================================================================
КОНСЕНСУС (GLM + GPT)
================================================================================

1. Q-сеть надо учить активнее при OS — да.
2. Вариант C: отдельные config flags для обычного режима и OS-режима.
3. Full pass по Q-buffer — НЕТ. Q-buffer persistent (не очищается),
   старые transitions, нет target_q_net → bootstrapping drift при
   слишком большом числе steps.
4. Не adaptive (B) — непредсказуемое время итерации.
5. Риск не overfitting, а TD instability / bootstrapping drift.
   Target строится через текущий q_net под no_grad, нет отдельного
   target_q_net. 5 steps при OS — безопасно, 20-50 — нет.
6. Диагностика: Train/QSteps, Time/QTrain, os_q_baseline_abs_error.

================================================================================
ИСПРАВЛЕНИЯ
================================================================================

1. config.yaml
   - q_train_steps_per_iteration: 2 (обычный режим, как раньше)
   - q_train_steps_with_os: 5 (если в итерации были OS-узлы)

2. src/utils/config.py (_DEFAULTS)
   - q_train_steps_per_iteration: 2
   - q_train_steps_with_os: 5

3. src/core/deep_cfr.py (DeepCFRAgent.__init__)
   - self.q_train_steps_per_iteration = cfg_get(...)
   - self.q_train_steps_with_os = cfg_get(...)

4. src/training/train.py (train_self_play_multi)
   - После traversal: проверка os_traversing_nodes > 0
   - Если OS активен → q_steps = q_train_steps_with_os (5)
   - Иначе → q_steps = q_train_steps_per_iteration (2)
   - Цикл: for _ in range(q_steps): train_q_network()
   - Логирование: avg Q loss, steps count, время
   - TensorBoard: Train/QSteps, Time/QTrain

================================================================================
ОЖИДАЕМЫЙ ЭФФЕКТ
================================================================================

С OS (~300 записей/итерацию в q_buffer с OS-узлов):
  - 5 Q steps × 256 batch = 1280 записей используется
  - Q быстрее сходится → Q-baseline точнее → OS-regrets тише
  - Петля самоусиления: лучше Q → лучше regrets → лучше advantage

Без OS:
  - 2 Q steps — как раньше, ничего не меняется

================================================================================
РИСКИ И МИТИГАЦИЯ
================================================================================

1. TD instability: semi-gradient TD без target_q_net.
   5 steps — безопасно. Мониторить Loss/QNetwork.
   Если Q-loss растёт — уменьшить q_train_steps_with_os.

2. Время: +~1-3 сек за итерацию (Q-сеть маленькая, 2 слоя × 128).
   Traversal 30-60 сек → незаметно.

3. Bootstrapping drift: нет target_q_net, target через текущий q_net.
   Не проблема при 5 steps. Если понадобится >10 — добавить target_q_net.

================================================================================
ДИАГНОСТИКА
================================================================================

Ключевая метрика: os_q_baseline_abs_error_mean
  = |Q(s, sampled_action) - v_sampled|, усреднённая по OS-узлам

Если после усиленного Q-training эта метрика падает — всё работает.
Если не падает — Q-сеть не сходится, проблема глубже.

Новое в TensorBoard:
  - Train/QSteps — сколько Q steps за итерацию
  - Time/QTrain — время обучения Q
