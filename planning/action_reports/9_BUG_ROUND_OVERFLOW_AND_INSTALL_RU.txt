ФИКС #9: ТРИ СВЯЗАННЫХ БАГА, СЛОМАВШИХ СХОДИМОСТЬ ТРЕНИРОВКИ
================================================================================

После применения фиксов #1-#8 тренировка перестала показывать профит против
рандомных агентов, несмотря на 1200 traversals × 16000 итераций. Анализ
выявил три проблемы, возникшие при упрощении кода. Все связаны с тем,
что установленный пакет pokers оказался непатченным (см. Баг 9B).

ВАЖНО: Точный механизм регрессии тренировки не установлен
окончательно. Ошибок HighBet в логах тренировки не наблюдалось.
Исправления ниже — это защитные коррекции подтверждённых дефектов
кода, но какой именно фактор (или комбинация) вызвал регрессию —
теория, а не доказанный факт. Тренировка сразу улучшилась после
применения этих фиксов и переустановки патченного pokers.


================================================================================
БАГ 9A: ПЕРЕПОЛНЕНИЕ float ПОСЛЕ round() — РЕЙЗ ПРЕВЫШАЕТ ОСТАТОК ФИШЕК
================================================================================

Статус:    ИСПРАВЛЕН
Критичность: КРИТИЧЕСКАЯ (тихо ломает сходимость тренировки)
Файлы:    src/core/deep_cfr.py (action_type_to_pokers_action)
          src/agents/random_agent.py (choose_action)

────────────────────────────────────────────────────────────────────────────────
ПРОБЛЕМА
────────────────────────────────────────────────────────────────────────────────

При применении фикса #1 код был упрощён:
  - Добавлено: round(additional, 2) для борьбы с накоплением float-шума
  - Удалено: epsilon-safeguard (ORIG строки 266-282) как «избыточный при
    наличии Rust clamp»

Но round() может УВЕЛИЧИТЬ значение:

    remaining_after_call = 179.995       (float-шум из арифметики Rust)
    additional = min(X, 179.995) = 179.995
    round(179.995, 2) = 180.0           ← теперь additional > remaining!

    Rust получает: bet = call_amount + 180.0 > player.stake
    Без clamp: ошибка HighBet → state.status != Ok

Поток кода (до фикса):

    additional = min(additional, remaining_after_call)   # обрезка до remaining
    additional = max(additional, min_raise_increment)    # минимальный размер
    additional = round(additional, 2)                    # ← МОЖЕТ ПРЕВЫСИТЬ
    return Action(Raise, additional)                     # ← ОТПРАВЛЯЕТ НЕВАЛИДНОЕ

В ORIG был epsilon-safeguard, который ЧАСТИЧНО ловил это:

    # ORIG deep_cfr.py строки 266-282
    total_chips = call_amount + chosen_additional_amount
    epsilon = 0.00001
    if total_chips > available_stake + epsilon:
        chosen_additional_amount = available_stake - call_amount

Однако этот safeguard был НЕПОЛНЫМ: он пропускал значения, когда
overflow был в пределах epsilon (0.00001) от stake. Значения в диапазоне
(available_stake, available_stake + epsilon] всё равно доходили до Rust
и вызывали HighBet — это наблюдалось на практике при тренировке с ORIG.

Окончательным решением всегда был Rust clamp (фикс #1), который ловит
ВСЕ overflow независимо от величины. Epsilon-safeguard лишь снижал
частоту HighBet, но не устранял их полностью.

При упрощении кода epsilon-safeguard был удалён в расчёте на то, что
Rust clamp всегда доступен. В сочетании с добавлением round() (который
может давать overflow больше чем epsilon) и непатченным pokers (нет
Rust clamp) — round() overflow ТЕОРЕТИЧЕСКИ может вызывать HighBet.
Однако ошибок HighBet на практике в логах тренировки не наблюдалось.
Фикс носит защитный характер: устраняет подтверждённый дефект кода
независимо от наблюдаемой частоты.

────────────────────────────────────────────────────────────────────────────────
ВЛИЯНИЕ НА ТРЕНИРОВКУ
────────────────────────────────────────────────────────────────────────────────

ТЕОРЕТИЧЕСКОЕ влияние, если HighBet возникает при CFR-обходе:

    1. state.apply_action(raise_action) → status != Ok
    2. Обход пропускает ветку: action_values[Raise] = 0 (по умолчанию)
    3. Расчёт regret:
         ev = Σ strategy[a] * action_values[a]   (Raise вносит 0)
         regret[Raise] = 0 - ev                   → ОТРИЦАТЕЛЬНЫЙ при ev > 0
    4. Regret matching снижает вероятность Raise или портит сайзинг

ПРИМЕЧАНИЕ: Ошибок HighBet в логах тренировки не наблюдалось. Выше описан
теоретический путь повреждения в случае overflow. Safety clip добавлен
как защита в глубину — дефект кода реален (round() МОЖЕТ создать
значение выше remaining), даже если он не подтверждён как
причина регрессии тренировки.

────────────────────────────────────────────────────────────────────────────────
ИСПРАВЛЕНИЕ
────────────────────────────────────────────────────────────────────────────────

Добавлена защитная проверка ПОСЛЕ round() — один if:

  --- src/core/deep_cfr.py ---

      additional = round(additional, 2)
  +   # Защита от float overflow после round()
  +   if call_amount + additional > player_state.stake:
  +       additional = max(0.0, player_state.stake - call_amount)
      return pkrs.Action(pkrs.ActionEnum.Raise, additional)


  --- src/agents/random_agent.py ---

      additional = round(random.choice(options), 2)
  +   # Защита от float overflow после round()
  +   if call_amount + additional > player_state.stake:
  +       additional = max(0.0, player_state.stake - call_amount)
      return pkrs.Action(pkrs.ActionEnum.Raise, additional)

В отличие от epsilon-safeguard из ORIG (который пропускал значения
в пределах epsilon), эта проверка ловит ВСЕ overflow — любое превышение
stake обрезается, с нулевой толерантностью. Вместе с Rust clamp
(патченный pokers) это даёт два независимых слоя защиты.

Внёс ли этот фикс вклад в улучшение тренировки — неизвестно,
т.к. он был применён одновременно с переустановкой патченного
pokers (Баг 9B) и другими изменениями.

БАГ 9B: УСТАНОВКА НЕПАТЧЕННОГО pokers ЧЕРЕЗ requirements.txt
================================================================================

Статус:    ИСПРАВЛЕН
Критичность: КРИТИЧЕСКАЯ (аннулирует все Rust-фиксы #1, #4, #5)
Файлы:    requirements.txt

────────────────────────────────────────────────────────────────────────────────
ПРОБЛЕМА
────────────────────────────────────────────────────────────────────────────────

Локальная папка pokers/ содержит все Rust-патчи, наложенные предыдущим
агентом (clamp, all_broke, поля bb/sb, last_raise_increment). Эти патчи
существуют как незакоммиченные локальные изменения поверх коммита b1a48bd.

Однако requirements.txt содержал:

    pokers @ git+https://github.com/dberweger2017/pokers.git@b1a48bd...

При выполнении pip install -r requirements.txt pip скачивает код с GitHub
по коммиту b1a48bd — который НЕ содержит локальных патчей. Патченная
локальная сборка перезаписывается непатченной версией с GitHub.

Диагностический тест подтвердил:

    py -c "import pokers as pkrs; s=pkrs.State.from_seed(2,0,1,2,200.0,42); \
           print(hasattr(s,'bb'), hasattr(s,'last_raise_increment'))"
    → False False

Это означает:
  - state.bb не существует → min_raise_increment скатывается (см. Баг 9C)
  - state.last_raise_increment не существует → аналогично
  - Нет Rust clamp → overflow от round() вызывает HighBet (см. Баг 9A)
  - Нет фикса all_broke → возможны зависающие игры

БАГ 9C: ДЕГРАДАЦИЯ FALLBACK min_raise_increment С ~2.0 ДО 1.0
================================================================================

Статус:    ИСПРАВЛЕН
Критичность: ВЫСОКАЯ (ухудшает качество обучающего сигнала)
Файлы:    src/core/deep_cfr.py (action_type_to_pokers_action)
          src/agents/random_agent.py (choose_action)

────────────────────────────────────────────────────────────────────────────────
ПРОБЛЕМА
────────────────────────────────────────────────────────────────────────────────

При упрощении Python-кода во время фиксов #4/#5 цепочка fallback для
min_raise_increment была сокращена:

    ДО (test, упрощённый):
        min_raise_increment = ... if hasattr(state, 'last_raise_increment') ...
                              else ... if hasattr(state, 'bb') ...
                              else 1.0    ← ПЛОСКИЙ FALLBACK

    ORIG содержал эвристику:
        if state.min_bet > 0:
            likely_bb = state.min_bet       (если Preflop и pot <= 3*min_bet)
                    или state.min_bet / 2   (иначе)
            min_raise_increment = max(1.0, likely_bb)    ← обычно ~2.0

С непатченным pokers (нет state.bb, нет state.last_raise_increment) обе
проверки hasattr проваливаются, и min_raise_increment = 1.0.

Эффект: агент делает рейзы $1 в пот $20. Такие микро-рейзы:
  - Стратегически бессмысленны (почти не меняют пот-оддсы)
  - Создают шумный, неинформативный сигнал regret для CFR
  - Тратят глубину обхода на непродуктивные ветки
  - Делают значения Raise почти неотличимыми от Check/Call

Эвристика ORIG корректно оценивала BB ≈ 2.0 из state.min_bet,
обеспечивая более реалистичные размеры рейзов.

────────────────────────────────────────────────────────────────────────────────
ИСПРАВЛЕНИЕ
────────────────────────────────────────────────────────────────────────────────

Восстановлена эвристика ORIG как третий уровень fallback:

    if hasattr(state, 'last_raise_increment') and valid:
        min_raise_increment = max(1.0, float(state.last_raise_increment))
    elif hasattr(state, 'bb') and valid:
        min_raise_increment = max(1.0, float(state.bb))
    elif state.min_bet > 0:
        # Эвристика ORIG: оцениваем BB из min_bet
        likely_bb = state.min_bet if (Preflop и pot <= 3*min_bet)
                    else state.min_bet / 2
        min_raise_increment = max(1.0, likely_bb)
    else:
        min_raise_increment = 1.0

С установленным патченным pokers срабатывает первая ветка
(last_raise_increment = 2.0), и эвристика никогда не вызывается.
Она служит страховочной сеткой при несовпадении версий.

Применено одинаково к deep_cfr.py и random_agent.py.


================================================================================
ДОПОЛНИТЕЛЬНЫЕ ОПТИМИЗАЦИИ
================================================================================

При расследовании проблемы сходимости были также исправлены:

1. max_depth в _cfr_traverse_with_opponents (train.py строка 90):
     БЫЛО:  max_depth = 1000
     СТАЛО: max_depth = 200
   В cfr_traverse (deep_cfr.py) используется 200. Несоответствие
   заставляло mixed/checkpoint тренировку тратить вычисления на
   глубокую рекурсию в маловероятные состояния игры.

2. Пространство seed (train.py, 4 места):
     БЫЛО:  seed=random.randint(0, 10000)     → 10 001 уникальных раздач
     СТАЛО: seed=random.randint(0, 1_000_000) → 1 000 001 уникальных раздач
   При 1200 traversals × 16000 итераций = 19.2M обходов каждый из 10 001
   seed'ов встречался ~1920 раз — чрезмерная повторная выборка.

3. Удалены 11 блоков DEBUG из train_advantage_network (deep_cfr.py):
   Эти блоки срабатывали каждые 10 итераций, генерируя ~24 000 строк
   вывода за тренировку. Каждый блок итерировал все параметры сети
   дважды (нормы градиентов до/после clip). Удалены полностью — давали
   ~5-10% overhead и заслоняли полезный вывод в логе.
