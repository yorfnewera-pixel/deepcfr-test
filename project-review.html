Приоритетно · текущий режим

01Неверные правила heads-up

При двух игроках button получает BB, а другой игрок получает SB и ходит первым как префлоп, так и постфлоп. В стандартном HU button ставит SB и действует первым только префлоп. Обучение использует этот конструктор напрямую.

pokers/src/game_logic.rs:123–148 · 567–570 · train.py:1260–1268

02Младший стрит оценивается слишком высоко

A-2-3-4-5 распознаётся как стрит, но сравнивается с тузом как старшей картой. Поэтому он ошибочно обходит, например, 2-3-4-5-6. Это касается и стрит-флеша, и напрямую искажает награды при обучении.

pokers/src/game_logic.rs:698–726 · 742–770

03HU light-checkpoint не загружается в runtime

HU strategy получает 183 признака, включая два признака actor ID. Экспорт описывает вход как 181 признак без соответствующего признака режима. PolicyRuntimeAgent отвергает такой файл при проверке размеров; аналогично устроен загрузчик blueprint.

train.py:1389–1405 · deep_cfr.py:2217–2231 · policy_runtime/core.py:441–451

Другие ошибки · раскрыть детали

04 · Парные оценки поиска теряют соответствие частицRuntime search · достоверность gap / z-score

Награды добавляются в списки по мере завершения rollout, а не по particle_index. Разные действия могут завершиться в разном порядке. Затем списки вычитаются по индексам как парные: сравниваются разные частицы, искажаются стандартная ошибка и разделение выборки. Это затрагивает решение о переходе от blueprint к search.

rollouts.py:153–189 · 226–249 · policy.py:183–188

05 · На BB после лимпов запрещён checkИгровой движок · активный HU и другие режимы

Check запрещается при min_bet > 0, а не при положительной сумме необходимого колла. На BB без рейза разрешается нулевой call вместо check. Движение фишек эквивалентно, но action-slot и публичная история неправильные, что важно для модели и внешнего runtime.

pokers/src/game_logic.rs:595–607

06 · В multi-player теряются данные предыдущих traverserНе текущий HU · non-D2CFR, несколько обучаемых игроков

При advantage_buffer_reservoir: false буфер очищается внутри фазы каждого игрока, а обучение происходит после всех фаз. Остаются примеры только последнего игрока. При включённой очистке strategy-буфера аналогично теряются и его данные. Очистка нужна до цикла игроков.

deep_cfr.py:944–949 · train.py:1921–1964

07 · Увеличение replay-буфера при resume небезопасноНе текущий HU · восстановление обычного checkpoint

Восстанавливается только count строк, но сохраняется исторический cur_id. После увеличения capacity длина min(cur_id, capacity) может превысить число заполненных строк. Например: восстановлено 100 строк, но буфер объявляет 200 доступными. Sampling может читать неинициализированные данные.

deep_cfr.py:2127–2142 · buffers.py:205–225

08 · Режим opponent modeling содержит отсутствующий импортОтдельный сценарий обучения · ошибка запуска по коду

Модуль импортирует src.opponent_modeling.deep_cfr_with_opponent_modeling, которого нет в дереве src/. В представленном снимке этот сценарий не может пройти импорт.

train_with_opponent_modeling.py:9

Документация отстаёт. README:5–11 описывает 6-max, но config.yaml:3–10 включает HU. Пример продолжения использует multi_checkpoint, тогда как текущий режим сохраняет hu_checkpoint.
Порядок исправлений: правила HU и ранжирование комбинаций → контракт экспорта → буферы и статистика поиска. Настройка гиперпараметров не исправит обучение на неверных правилах.
Архитектура: Rust-движок → Python CFR / D2CFR → усреднённая strategy → независимый runtime; поиск использует beliefs и rollout. Обзор выборочный, не гарантия отсутствия других ошибок.
